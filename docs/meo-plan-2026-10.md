## 0. 要約

1. NAGOYA BITES は店舗を持たないメディアなので、**Google ビジネスプロフィール（GBP）には登録できない**（Google の規約）。「自分が地図で上位に出る」型の MEO は成り立たない。この計画では MEO を「**Google マップやローカル検索で店を探す人に、当サイトの『選ぶ理由』を届け、地図・電話・予約まで運ぶこと**」とする。
2. 調べて見つかった一番大きな穴は、**店の位置が全店ずれていること**。ホットペッパーの API は店ごとの座標を返しているのに、ビルドの途中で全店を 39 通りの「エリアの中心点」に上書きしている（`build.js:1713-1721`）。このため店舗ページに位置（geo）を出せず、トップの「現在地」ボタンも最寄りのエリアで絞るだけになっている。
3. 次の穴は、**地図リンクが「店名＋エリア」の検索で、どの店かを指定していない**こと。同じ名前の店や、チェーンの別の支店が開くことがある。Google の紐付けを確かめ済みの 4,237 店（営業中の 85%）は、店を一意に指す place_id で開ける。
4. 段階1（約 10 日・費用 0 円）で「位置を直す・地図リンクを店に結ぶ・地図のクリックを毎日数える・地名つきの検索を毎日数える」をやる。段階2で、直した位置を使って「現在地から近い順」と店舗ページの「近くの店」を作る。段階3（Google マップの公開リスト・掲載店へのお知らせ）はオーナーの判断待ち。
5. 効果は「地図のクリック」「地名を含む検索の表示とクリック」「現在地の利用」で測る。目標の数字は、段階1の後に基線を 2 週間取ってから置く（推測の目標を先に置かない・品質ゲート原則5）。

## 1. 前提：このサイトにとっての MEO

### 1.1 できないこと（規約で決まっている）

| 施策 | 結論 | 根拠 |
|---|---|---|
| GBP に NAGOYA BITES を登録する | できない。「営業時間内に客と対面するビジネス」だけが対象で、オンラインだけの事業は不適格 | Google ビジネスプロフィールのヘルプ https://support.google.com/business/answer/13763036 |
| 食べログ・Google の評価を集めて星（aggregateRating）にする | してはいけない。「他のサイトのレビューや評価を集計しない」 | https://developers.google.com/search/docs/appearance/structured-data/review-snippet （2026-09-08 更新）。当サイトも判断の記録 0009 で外し済み |
| Google の店舗情報（位置・評価・写真・口コミ）を保存して使い回す | place_id 以外は保存できない（place_id だけは無期限に保存してよい） | https://developers.google.com/maps/documentation/places/web-service/policies |

### 1.2 当サイトが関われる面（4つ）

| 面 | 人の動き | 当サイトの役目 | 今の状態 |
|---|---|---|---|
| A. 地図枠が出る検索 | 「栄 居酒屋 個室」と検索 → 上に地図枠、下に Web の結果 | Web の結果に、ハブ（エリア×ジャンル×条件）と特集で出る | ハブ 30 本中 28 本が Google に未認識（10-14） |
| B. 店名で調べる | 店名で検索 → 店の情報パネル・Google マップ | 店舗ページが、パネルに無い「選ぶ理由」「口コミ信頼度」で並ぶ | 店名検索の表示 9,647・CTR 0.82%・平均 13.8 位 |
| C. サイトから地図へ | 当サイトで選ぶ → Google マップで経路・保存・電話 | 正しい店の地図を一度で開く | 地図リンクが店名の検索。地図のクリックは毎日の集計に無い |
| D. いま近くで探す | スマホで現在地から探す | 近い順に「選ぶ理由」つきで見せる | 「現在地」は最寄りのエリアで絞るだけ（店の位置が無いため） |

A の「ハブを Google に見つけてもらい、中身を濃くする」は SEO 戦略の T7（SEO-123〜126・11-15 に判定）が受け持っている。この計画では重ねない。この計画が受け持つのは、A に効く「位置の事実」と、B〜D。

## 5. 施策

### 段階1 土台を直す（10-16〜10-24・費用 0 円・見た目はほぼ変わらない）

#### M0 地名を含む検索を毎日数える

- 何を: `scripts/fetch_gsc_metrics.js` が取得した全クエリ（今は上位 300 件しか保存しない・`QUERY_STORE_LIMIT`）から、地名（エリア名・県内の駅名・近く・周辺・駅前）を含むクエリの合計（表示・クリック・CTR・順位）を毎日 `data/gsc_metrics.json` に残す。地名の語は既存の `scripts/lib/station_names.js` と `data/area_genre_pages_policy.json` から取る（新しい辞書を作らない）
- 達成条件: `gsc_metrics.json` に地名つきの合計が入り、その値が上位 300 件だけで数えた値（10-15: 62 件・1,529 表示）以上になる

#### M1 店ごとの位置を直す（ホットペッパーの座標を使う）

- 原因: `build.js:625` でホットペッパーの API の店ごとの緯度・経度を入れているのに、`build.js:1713-1721` が全店にエリアの中心点を上書きしている
- 何を: ホットペッパーの座標がある店はそれを残し、座標精度を `hotpepper` にする。無い店だけエリアの中心点（`area`）にする。次の検査に通らない座標は使わない（エリアの中心点に倒す）:
  1. 愛知県の範囲の中にある
  2. 掲載のエリアの中心点から一定の距離の中にある（距離の分布を測ってから決める。目安 5km）
- 確かめ方: 本番に入れる前に、標本 50 店で、ホットペッパーの座標と Google マップの店の位置の差を測る。ほとんど（目安 45 店以上）が 100m 以内なら入れる。Google の位置は比べるだけで保存しない（規約）。Places の呼び出しは 50 回で、無料枠の中
- 達成条件: 営業中の店のうち座標精度が `hotpepper` の店が 95% 以上。ビルドの前後で店の数・店舗ページの数が変わらない
- 判断の記録: 「店の位置の正本はホットペッパーの座標。エリアの中心点は無いときの代わり」を `docs/decisions/` に残す

#### M2 地図リンクを店に結ぶ（place_id）

- 何を: 地図リンクを Google の公式の形 `https://www.google.com/maps/search/?api=1&query=<店名 住所>&query_place_id=<place_id>` にそろえる。place_id を付けるのは「電話確認」の欄がある店（紐付け先の住所・店名が掲載と合うと確かめ済み・4,237 店）だけ。それ以外は店名＋住所（住所が無ければ店名＋エリア）の検索にする。電話のボタンと同じ判定を使うので、新しい基準は増えない
- 場所: 店舗ページ（`gen-store-pages.js:745`）・トップのカードとクイックビュー（`index.html` の `gmap()`）。URL の作り方は 1 か所（`scripts/lib/maps_link.js`）に置き、index.html へは `scripts/lib/related_stores.js` と同じく `--apply` で写す
- 達成条件: 店舗ページの地図リンクのうち place_id つきが、電話確認の店の割合（約 85%）と一致する。電話確認の無い店に place_id が付いていないことをテストで確かめる。計測のイベント名（`cta_gmap_click`）は変えない

#### M3 構造化データに位置と地図を足す

- 何を: 店舗ページの Restaurant に `geo`（M1 で位置を確かめた店だけ）と `hasMap`（M2 の URL）を足す。`openingHours` は今の文字のまま（形が店ごとにばらばらで、曜日と時刻に機械で直すと誤りが混じるため、今回は触らない）
- 達成条件: 標本 20 本で geo・hasMap が出ている。`node scripts/audit_inline_js_syntax.js --check --only stores` が通る
- 注意: Google はこの 2 つで検索結果の見た目が変わるとは言っていない。効果は M0 の数字と店舗ページの表示で見る

#### M4 地図のクリックを毎日数える

- 何を: `scripts/fetch_ga4_views.js` で `cta_gmap_click` を店と場所（店舗ページ・クイックビュー・カード・ジャーナル）ごとに数え、`data/store_referrals.json` に「地図」として別の欄で残す。予約送客には混ぜない（判断の記録 0009）
- 達成条件: 翌日の `store_referrals.json` に、地図のクリックの 30 日の合計と上位の店が入る。`docs/kpi-weekly.md` の週次の表に 1 行足す

### 段階2 位置を使って選びやすくする（10-27〜11-07 に作り、基線が取れた後の 11-08 に公開）

画面が変わるので、Designer のレビューと `node scripts/audit_design_system.js --check` を通す（制約12）。

#### M5 「現在地」を「近い順」にする

- 今: 現在地から一番近いエリアを選んで絞るだけ（`index.html:6812-6838`）
- 変える: 店ごとの位置がある店を、現在地からの直線距離が近い順に並べ、カードに「約 350m」のように出す。位置は端末の中でだけ使い、送らない・保存しない。「徒歩◯分」は書かない（道のりを測っていないため・推測しない）
- 計測: `geo_search`（押した回数・位置を許可された回数・出した件数）
- 達成条件: 栄・名駅で、近い順の上位 10 店がすべて 1km 以内（実機で確かめる）。位置を許可しなかったときは今と同じ動き

#### M6 店舗ページに「近くの同じジャンルの店」

- 今: 「似た店」はエリアとジャンルで選ぶ（判断の記録 0022）。同じエリアでも 1km 以上離れることがある
- 変える: 位置がある店は、同じジャンルで 500m 以内の店を近い順に最大 3 店。足りなければ今の選び方で埋める。0022 の見直しとして判断を残す
- 計測: 既存の `internal_link_click`（block を分ける）

#### M7 ハブに「駅から近い店」の目印を足す（SEO の T7 と一緒に判断）

#### M9 掲載店へのお知らせ（判断 4）

- 懸念: 外部への送信になる。広告ゼロ（編集独立性）の説明が要る。Strategist の別計画にする
- 推奨: 今はやらない（段階1・2の数字が出てから）

## 11. 危ないところと対策

| 危ないところ | 対策 |
|---|---|
| ホットペッパーの座標がずれている店がある | 標本 50 店の比較と、エリアの中心点からの距離の検査で弾く。弾いた店は今と同じ（位置を出さない） |
| place_id が別の店を指している | 電話確認の店だけに付ける（電話のボタンと同じ判定） |
| 地図リンクの形を変えると、計測が途切れる | イベント名（`cta_gmap_click`）と送る値を変えない |
| build.js の変更で店の数が変わる | 座標の欄しか触らない。ビルドの前後で店の数・店舗ページの数が同じことを確かめる |
| 位置の情報で利用者が不安になる | 現在地は端末の中でだけ使い、送らない・保存しないと画面に書く |

この計画の外で見つけたこと: 2.4 の Google の紐付けの不一致 1,523 件のうち、決められない 332 件は、地図リンクには使わないが評価の表示には今も使っている。P-142 の基準（住所が別の場所なら外す・同じ建物は人が確かめる）の残りで、扱いは DataKeeper の課題として別に見る。
