## 1. 要約

### いちばん大きな問題（6つ）

1. **店の選び方の説明が、実態と違う。** 公開している HTML の98%に、人が全店を選んだ・書いたと読める言い方がある。実際は、データの取得と AI による分析・文の作成、点数による掲載店の入れ替えが中心。選定理由が付いている店は 5,004店のうち151店。トップの FAQ の構造化データも、無い機能と、事実と違う選び方を書いている（U-01〜U-06・U-15）。
2. **検索から人が着く店舗ページが使いにくい。** 検索の表示の76%は店舗ページに出ている。予約のリンクは3〜4画面下。97%のページが、その店を載せていない特集を「登場する特集」として案内している。基本情報は5項目だけ（U-30〜U-38）。
3. **壊れている機能がある。** 保存した店が見えない。共有のリンクで店が開かない（ページに入っている50店のほか）。モーダルを開いて「戻る」を押すと、モーダルではなくページごと前に戻る。「店舗一覧」を押すとトップへ戻される（U-16・U-23・U-25・U-27）。
4. **写真の出し方が、規約と自分たちの基準に合っていない疑いがある。** HotPepper の写真を外部の変換サービスで加工している。143店のヒーローが壊れた画像。利用者が投稿した写真に撮影者の表示が無い（U-36・U-57〜U-59）。
5. **重い。** どのページでも、いちばん重いのは Web フォント（ページあたり 0.8〜2.0MB）。トップの LCP は約10秒、初めて見られる店の店舗ページの LCP は約7秒、ハブの CLS は 0.652 になる回が多い（10周のうち7回）。TBT は測定機の電源で割れる（U-52〜U-56・U-84・2.2 節）。
6. **検索エンジンに渡している情報に誤りがある。** 店舗ページの構造化データの位置の情報は、店の位置ではなくエリアの中心点。4,939ページで39通りしかない（U-73）。

### 直し方の要点

- **店舗ページを先に直す。** 予約を最初の画面と下の固定の帯に置き、基本情報を足し、載っている特集・記事は実際の掲載だけにする（段階2）。
- **トップのモーダルは、店舗ページと同じ部品のクイックビューにする。** 店舗ページへのリンクを付け、「戻る」で閉じられるようにする（段階3）。
- **写真が主役。** HotPepper の写真は加工せず、配られている比率（正方形）のまま使い、引き伸ばさない。写真の無い店は、Instagram の投稿か、ジャンルの印にする。
- **カードは店舗ページへのリンク（`<a href>`）にする。** 新しいタブで開け、検索エンジンからもたどれる。
- **似た店は、理由を1行で言える店だけにする。** 同じエリア・同じジャンル・予算の近さで選ぶ。足りなければ数を減らし、関係の薄い店で埋めない。
- **スマホは下部タブ4つ（探す・特集・読む・保存）にする。** 常に浮いている部品を減らす。
- **URL は1本も変えない。** トップの状態は、今のハッシュの名前のまま残す。
- **言い方は、選び方の実態どおりに書く**（5.5 節）。

### 2.2 表示速度の測定

- 条件: 412×823・DPR 1.75（Android の UA）、CPU を4倍遅く、遅延 150ms・下り 1.6Mbps・上り 750kbps、キャッシュなし、初回の表示。GA4 などは止めた。
- 測ったもの: TTFB・FCP・LCP（とその要素）・CLS・TBT（FCP より後の長いタスクの合計）・読み込み完了・通信量（種類別・ホスト別）・DOM の要素数。
- 回数: 設計のときは各ページ1回（トップとハブは2回測り、ほぼ同じ値だった。トップ LCP 10.4s／10.5s、ハブ CLS 0.654／0.652）。基線は I-02 で、ページ種別を一周する順に10周ずつ測り直した（2026-10-11。3.6 節）。店舗ページは、同じ店を測り続けると画像変換サービスのキャッシュで速く出るので、店を替えて測る値（`store-sample`）も取る（判断の記録 0019）。
- 1回の測定は揺れる。**TBT とハブの CLS は、測定機（Mac）の電源で割れた**（同じページ・同じ内容でも、TBT が数十 ms と数秒、ハブの CLS が 0.013 と 0.652）。割れ目の時刻が、電源が充電器からバッテリーに切り替わった時刻と一致した【確認済み】。この Mac は低電力モードが「バッテリー駆動のときだけ」入る設定なので、電源そのものか低電力モードかは区別できていない【推測】。そのため、順位や前後の比較に使うときは、**同じ日に、同じ電源（標準は充電器）で**、10周の中央値・最小〜最大・目標超の回数を見る（第10章・判断の記録 0018）。
- 測定の手順は付録 A（`docs/qa/uiux-2026-10/perf.js`・`perf_summary.js`）。

## 4. 優先順位と改善案

### 4.1 決め方

- 優先度は CLAUDE.md の基準に合わせる（P0: ブランドの毀損・データの誤り／P1: UX の劣化・SEO・競合に明確に負けている所／P2: 計画的な改善／P3: 磨き）。
- 同じ優先度の中では、次の順に先にする。
  1. **読者に事実と違うことを伝えているもの**（選び方の説明・載っていない特集の案内・違う位置の情報）。
  2. **検索から人が着くページ**。検索の表示の 76%（35,721 のうち 27,004）は店舗ページに出ている。トップのモーダルが開いたのは30日で63回。だから店舗ページを、トップの一覧より先に直す（3.10 節）。
  3. **小さく直せて効果が大きいもの**（フォント・写真・壊れた機能）。
  4. **ページの部品**（カード・写真・ボタン）を先に作り、**ページの骨組み**（下部タブ）は後にする。部品が決まる前に骨組みを変えると、2回作り直すことになる。
- 改善案は36件。1つの改善案が、関係する問題をまとめて直す。どの問題も、どれかの改善案に入っている（4.2 節の「直す問題」の列）。

- **PC（768px〜）**: ヘッダーに同じ4項目＋検索欄。下部タブは出さない。
- **浮いている部品の整理**:

  | 今あるもの | これから |

  | 下部の固定検索バー（トップ） | 下部タブ「探す」と画面上部の検索欄に統合 |
  | 上部の固定「絞り込み」 | 一覧画面のツールバー（1行）だけに置く |

**写真の比率と大きさ** — HotPepper の写真は、確かめた標本ではすべて正方形だった（`_238`＝238×238・`_480`＝480×480・原寸＝880×880 と 1,280×1,280）。原寸は 2026-08-05 の実測で 3,243件が 480px を超え、中央値 1,080px・最大 1,280px（968件は原寸を取れなかった。`data/hotpepper_master_probe.json`）。

- 比率は 1:1 のまま使う。横長の枠に入れて切り抜かない（規約の「加工」に当たるかの議論を避けるため。CSS での切り抜きも含めない）。今の特集は 67頁がヒーローの枠を 16:7 にしていて、正方形の写真の上下を大きく切っている（3.5 節）。
- **表示の幅は、写真の横幅の半分まで**にする。2倍の画面で引き伸ばさない上限で、写真ごとに機械的に決まる。
  - `_480` の写真は幅 240px まで。原寸（1,080px）なら画面幅いっぱい（最大 480px）まで。
  - 写真の横幅は、URL の形（`_480`）と原寸の実測（`data/hotpepper_master_probe.json`）から生成時に決める。

| 置き場所 | 表示の幅（390px の画面） | `_480` しか無い店 | 原寸がある店 |

- 写真の無い店（148店・全体の 3%）: 大きな代わりの絵（今の「写真準備中」）は出さない。一覧ではジャンルの印を薄い面に置いた 96px の四角、詳細では写真の枠ごと出さずに店名から始める。Instagram の投稿がある店（101店）は、詳細でその埋め込みを写真の代わりに上に出す。

- 表示の前に画像を変換するサービス（今の wsrv.nl）は通さない。HotPepper が配る URL をそのまま使う（3.7 節）。

**動きと反応**

- シートの開閉 200ms（ease-out）。押したときの色の変化 100ms。`prefers-reduced-motion` では動きを止める。

- 0件のときは「外すと増える条件」をボタンで出す（例「予算の条件を外す（+32軒）」）。
- 隠れた操作（長押し・スワイプだけでできる操作）は作らない。スワイプでできることは必ずボタンでもできる。

### 5.5 文言の方針（店の選び方の書き方）

オーナーの指示: 「店舗の選定にはAIによる情報収集・分析を活用しています。人間の飲食業界関係者がすべての店舗を選定しているような表現は使用しないでください。」

この指示を、サイトの全ページ・生成器・テンプレート・エージェントの手順書に当てはめる。

**書き方の決まり**

1. 店を「誰が・何で」選んだかは、実態どおりに書く。AI で情報を集めて分析していることを隠さない。
2. 「業界人」「現役の店長」「飲食のプロ」「中の人」を、選んだ人・書いた人の意味で使わない。
3. 人が確かめたものは、確かめた記録があるときだけ、そう書く。
   - 選定理由（editorReason・151店）の根拠は、今も `scripts/lib/editor_reason.js` の語（訪問済・店主取材済・公開情報ベース・公開情報ベース（自動収集）など）で出している。この語を使い続ける。
   - 自動で作った選定理由（55件）には、確認した人の記録（`data/editor_picks.json` の `automation.reviewed_by`）がある。
   - おすすめ文（`data/recommendations.json` 4,635件など）は、規則で作った文（`scripts/fill_recommendations_json.js`）と AI で作った文（`fill_recommendations.js`）が混ざり、確かめた記録が無い。「集めた情報の要約」として出し、人が書いたようには見せない。
4. 運営者の経歴は「運営について」のページに、事実だけを書く。店の選び方の説明とは混ぜない。
5. 選び方の説明は1か所（`editorial-policy.html`）に置き、各ページからはそこへリンクする。
   - 書くのは実際の手順だけ（データの出どころ・AI で集める情報・実在の確かめ方・口コミ信頼度・閉店の扱い）。

**書き換えの候補**（場所の一覧は第3章 3.1）

| 今の言い方 | 何がまずいか | 書き換えの候補 |
|---|---|---|
| 飲食のプロが、名古屋だけを深く選んだ。（トップの見出し） | 人が全店を選んだと読める | 名古屋の飲食店を、確かめられる情報で選ぶ。 |
| 現役の店長が編集（実績帯）／現役の飲食店マネージャーが編集する（フッター） | 同上。「編集」が「選定」と読める | 実績帯から外す。運営者のことは「運営について」へ |
| 編集部の視点 — 現役飲食店マネージャーが編集（モーダル） | 同上 | この店のポイント（根拠の語は決まり3のとおり） |
| 業界人メモ（モーダル） | 人が書いたと読める | 知っておきたいこと |
| 業界人が厳選（特集） | 人が選んだと読める | 条件で選んだ◯軒（条件は「この特集の選び方」に書く） |
| 現役飲食店マネージャーが厳選（特集一覧） | 同上 | 掲載の基準で選んだ店の特集 |
| 〜を業界人が読む（ジャーナルの題） | 人が書いたと読める | 〜を読み解く／〜の見どころ |
| 飲食業界の中の人が（ジャーナル一覧） | 同上 | 名古屋の新店と話題を、毎日まとめています |

**範囲**

- サイトの表示: トップ・モーダル・店舗ページ・ハブ・特集・ジャーナル・一覧ページ・`editorial-policy.html`・メタ説明・JSON-LD の説明文。
- 生成器とテンプレート: 次に作るページで同じ言い方が戻らないようにする（`gen_industry_features.js`・`journal/_template.html`・日次ジャーナルの生成手順など。場所は第3章）。
- 手順書: `CLAUDE.md` の競争優位の節（「現役飲食人運営による解釈層」「業界人の目利き」「業界人 推薦」を狙う語にする方針）と `agents/*.md`。CLAUDE.md の書き換えはオーナーの承認が要る。
- 公開済みの記事の題（`<title>`・h1）を変えると検索順位に影響しうる。新しい記事から先に変え、過去の記事は変える本数と前後の検索の数字を決めてから変える（第8章）。

**オーナーに確かめること**（確かめるまでは、上の決まりの側に倒す）

- 運営者の経歴をサイトに書くか。書くなら、その文。
- 「編集部推薦」の店（`data/manual_stores.json` の `編集部推薦`）を、誰がどう選んでいるか。
- 「業界人」を含む検索の狙い語（CLAUDE.md の「勝つ領域」）をやめるか。
- 選定理由の根拠の語「業界内で評判」（12店）を、どう書くか。今は根拠を第三者が確かめられない（制約10）。

```
  ├(特集)→ 特集 ─(店のカード)→ 店舗ページ
  ├(読む)→ ジャーナル ─(この記事の店)→ 店舗ページ
  └(エリア)→ ハブ ─(カード)→ 店舗ページ ─(似た店)→ 店舗ページ
                                       ├(もっと探す)→ ハブ
                                       └(載っている特集・記事)→ 特集・ジャーナル
保存（下部タブ）→ 保存の画面 ─(比べる)→ 比べる表 ─(予約)→ 外部
```

- トップの一覧だけは、カードを押すとクイックビュー（シート）を開く。ハブ・特集・ジャーナル・店舗ページでは、カードを押すと店舗ページへ移る。
  - トップは店のデータを読み込み済みなので、その場で開ける。
  - 静的なページで同じことをするには `data/stores.json`（約1.5MB）を読む必要があり、重くなる。
  - どのページでも「カードを押すとその店が開く」という点は同じにする。
- 外部（HotPepper・食べログ・地図）へは、今どおり新しいタブで開く。電話はタブを開かない（スマホは発信の画面、PC は番号を出す。7.3 節）。予約の計測（`nbReserveExit`・`cta_click`・`cta_call_click`）は今のまま使う。

### 7.2 URL と「戻る」

トップの状態は今、URL のハッシュ（`#q=` `#genre=` `#tag=` `#ward=` `#pref=` `#cap=` `#store=`）に入っている（`index.html:9130` の `pushHash`・:9153 の `readHash`）。この形は変えない。すでに共有されたリンクと、店舗ページから来るリンクが動き続けるようにするため。

| 状態 | URL | 戻るで | 再読み込みで | 共有したとき |
|---|---|---|---|---|
| トップ | `/` | 前のサイト | 同じ | `/` |
| 一覧 | `/#genre=…&ward=…`（今の名前のまま。並び順 `sort` とページ `page` を足す） | 検索の前のトップ（スクロール位置も） | 同じ一覧 | 同じ一覧 |
| 絞り込み・並び替えのシート | URL は変えず、履歴に印だけ足す | シートが閉じる | 一覧 | — |
| クイックビュー | 一覧のハッシュに `store=ID` を足す（今の `#store=` と同じ名前） | 一覧（スクロール位置そのまま） | 一覧＋同じ店が開く | 店舗ページの URL `/stores/ID.html` |
| 保存 | `/#view=saved`（新しい名前。今の `readHash` は知らない名前を読まないので、ぶつからない） | 直前の画面 | 保存 | — |
| 店舗ページ・ハブ・特集・ジャーナル | 今の URL のまま（変えない） | ブラウザの通常の戻る | — | その URL |

- 今は条件を変えても履歴を足さない（`replaceState` だけ・:9148）。これを次のように分ける。
  - 条件のチップ・並び替え: 今どおり置き換える。チップを押すたびに履歴が増えて「戻る」が効かなくなるのを防ぐ。
  - 検索の実行・シートを開く・クイックビューを開く・保存の画面: 履歴を1つ足す。
- シートとクイックビューを閉じる方法は4つ（×・下へのスワイプ・背景を押す・戻る）で、どれも同じ結果になる。
  - × などで閉じたときは、足した履歴を1つ戻して消す。
  - こうしないと、閉じた後に「戻る」を押してもシートの分が残り、1回で戻れない。
- `#store=` は、全店のデータを読み終えてから店を探す。今はページに入っている50店の中だけを探すため、それ以外の店（たとえば GSC の表示1位の店）は開かない（3.4 節）。
- 店舗ページのパンくずと「もっと見る」の行き先は、ハブがあればハブにする。ハブが無い店（459ページ）は今 `../#area=` に行くが、トップは `area` を読まない。行き先を、その店のエリアのハブ（10群）に変える。トップに新しい名前を足すより、生成器を直す方が確実なため。
- 店舗ページから一覧に戻ったとき、前のスクロール位置と条件を戻す。
  - ブラウザのページ保存（bfcache）を妨げる `unload` の処理を置かない。
  - 保存されなかったときに備えて、`sessionStorage` に条件と位置を残す（失敗しても普通に表示できるよう try/catch で囲む）。
- ハッシュは検索エンジンに送られない。一覧・クイックビュー・保存は、検索エンジンから見るとすべてトップ（`/`）の1ページで、canonical も今どおり `/`。

| ♡（保存） | 保存する／外す | ♡が塗りになる。「保存しました［元に戻す］」を4秒出す。下部タブの数が変わる | `aria-pressed` で状態を伝える。押せる範囲は 44px 四方 |
| 写真の列 | 横にスクロールする（止まる位置をそろえる） | 次の写真が端に少し見える（続きがあると分かる） | 必ず「すべて ›」のボタンも置く |
| クイックビューの前・次 | 一覧の隣の店へ | 中身だけ入れ替え、シートは開いたまま | ボタンでもスワイプでも同じ。最初と最後では押せない見た目にする |
| シート | 下へスワイプ・×・背景・戻るで閉じる | 200ms で出入り | 開いている間は後ろの画面を操作できない（`inert`）。閉じたら、開いたボタンに焦点を戻す |
| 絞り込みのチップ | 選ぶ／外す | 金色の枠と ✓。下のボタンの件数がすぐ変わる | 件数はその場で数えた実数。0軒になる組み合わせでも押せるが、件数は 0 と出す |
| 並び替え | 選ぶとすぐ並べ替えて閉じる | 選んだ順の名前がツールバーに出る | 「おすすめ順」には根拠の1行を付ける |
| 検索欄 | 入力中に候補（エリア・駅・ジャンル・店名）。Enter か候補で一覧へ | 候補は5件まで | `type="search"`・`enterkeyhint="search"`。× で消す |
| 予約ボタン | 予約先を新しいタブで開く | 押した瞬間に色が変わる | 行き先をボタンに書く（「HotPepperで予約」）。一番手（塗り）は、予約先があれば予約、無ければ電話（出せる店だけ）、どちらも無ければ地図（下の表）。押しても何も起きないボタンは作らない |

**行動バーに出すボタン**（店の数は `counts.js` の「設計が使うデータ」の phone・2026-10-11）

| 店の種類 | 店の数 | 行動バー |
|---|---|---|
| 予約先があり、電話を出せる | 4,215 | [予約]（塗り）・[電話]・[地図] |
| 予約先があり、電話を出せない | 712 | [予約]（塗り）・[地図] |
| 予約先が無く、電話を出せる | 59 | [電話する]（塗り）・[地図] |
| 予約先が無く、電話も出せない | 18 | [地図を開く]（塗り） |

- 予約先は HotPepper か食べログの店のページ。電話を出せるのは、Google の紐付け（placeId）があり、次の確かめ方で合った店。
- 電話を出せない730店の内訳: placeId が無い327店、紐付けが掲載の店と合うと確かめられない403店（住所が別の場所120店・住所で比べられず店名も合わない283店）。
- 今は、店舗ページは予約先の無い63店だけ、クイックビューは placeId のある4,677店すべてにボタンを出していて、2つの画面で規則が違う（U-38）。

**電話の紐付けの確かめ方**（生成のときに行う）

1. `data/places_resolved.json` の Google の住所と、掲載の住所を `compareJpAddress()`（`scripts/lib/store_link_identity.js`・食べログのリンクの照合と同じ判定）で比べる。同じなら出す。別の場所なら出さない。
2. 住所で比べられない店（掲載の住所が無いなど）は、店名を `namesMatch()`（`scripts/lib/store_name_match.js`・架空店の確認と同じ判定）で比べ、合うときだけ出す。
3. 店名だけで決めないのは、この判定が厳しく、住所が同じ同じ店でも表記の違いで合わないため（例「cafe chikaku」と「チカク」）。住所で比べると、別の支店を見分けられる（例「鮨食人 五と二 矢場町」と「桜山鮨食人 五とニ」）。
4. ISSUE-147 で別の店と確かめて外した紐付け（`rejected: true`）は使わない。

**番号を取れなかったとき**

| 結果 | 出す文 | 次の手 | 計測の result |
|---|---|---|---|
| 番号を取れた | スマホは発信の画面、PC は番号 | — | ok |
| Google に番号が無い | 「この店の電話番号は Google に登録がありません」 | 地図を示す | no_number |
| Google では閉業 | 「Google の店舗情報では閉業となっています」（発信しない） | 地図を示す | closed |
| その端末の1日の上限（20回） | 「本日はこれ以上確かめられません」 | 地図を示す | device_limit |
| サイト全体の1日の上限 | 「いまは電話番号を確かめられません」 | 地図を示す | quota |
| Google が断った・店の情報が無い・通信の失敗 | 「いまは電話番号を確かめられません」 | 地図を示す | denied・not_found・error |

- 今は、番号を取れた場合以外はすべて「電話番号なし」と出している（U-83）。写真で決めている「取りに行けなかった」と「候補が無い」を分ける考え方（CLAUDE.md の本文写真の原則3）と同じにする。
- 閉業かどうかは、押した時点の Google の店舗情報で、掲載を外す判断には使わない（店の営業は `data/store_liveness_reviews.json` の手順で一次情報を2つ確かめる）。closed と not_found の件数は DataKeeper が見る。
- サイト全体の1日の上限は、写真の取得などと共有している（`index.html:10135` の注記）。電話は押したときにしか番号を取らないので、ページが見られた回数では上限を使わない。

**予約先がある店でも、電話を帯に残す理由**

- 今のクイックビューは、予約先がある店でも帯に電話を出している。帯から外すと、電話で予約したい人の操作が増える。
- 押したときにしか番号を取らないので、出しておくだけでは上限を使わない。直近30日に押されたのは2回（`data/store_referrals.json`）。
- 見直す条件: 計測の result に quota が出た日があったとき。原因（電話か、写真の取得か）を確かめ、電話なら、予約先がある店の電話を基本情報の行へ移す（今の店舗ページの作り）。

- 長押し・2本指など、ボタンでできない操作だけの機能は作らない。
- 何かを押した結果は、0.1秒以内に見た目で返す（読み込みに時間がかかるときはスケルトンを出す）。

### 7.4 似た店（関連店）の選び方

回遊を増やすためだけの、関係の薄いおすすめはしない。理由を1行で言える店だけを出す。

今は2つの選び方がある（3.4 節）。

- 店舗ページ（`gen-store-pages.js:346` の `buildRelatedStores`）: 同じエリア・同じジャンルを優先し、Google 評価と口コミ数の大きい順に4軒。
- モーダル（`index.html:10540` 付近）: ジャンル名の先頭の語を含む店を、データの並び順で12軒。エリアも予算も見ないので、同じジャンルの店ではどの店を開いても同じ12軒が出る。

これを1つの判定にそろえる。

| 順 | 条件 | 理由として出す文 |
|---|---|---|
| 1 | 同じエリア群・同じジャンル・予算帯が同じか隣 | 「同じ栄の焼肉・予算が近い」 |
| 2 | 同じエリア群・同じジャンル | 「同じ栄の焼肉」 |
| 3 | 隣のエリア群・同じジャンル・予算帯が同じか隣 | 「伏見の焼肉・予算が近い」 |
| 4 | 同じエリア群・その店と同じ条件（個室・宴会など。ハブの13軸と同じ判定） | 「栄で個室がある店」 |

- 材料は足りている。エリア群（10）とジャンル（17）が同じ店が4軒以上ある店は 95.6%、予算帯（5段）まで同じ店でも 81.9%（2026-10-11 の `data/stores.json` で集計）。
- 同じ順の中では、同じ最寄り駅 → 予算帯の近さ → 店の ID の順に並べる。評価の高い順にはしない。
  - 今の店舗ページの似た店のリンク 19,880本は、840店（店舗ページの約17%）に集まっている。上位50店で 42.6%、多い店は 422本。評価順だと、どのページからも同じ人気店ばかりを指すため。
  - 1店が似た店として出るページの数に上限を設ける。上限の値は、そろえた後の分布を測ってから決める（品質ゲート原則5）。
- 閉店リストの店・店舗ページの無い店・誘導ページ（古い ID）は出さない。
- 最大6軒。条件に合う店が少なければ、その数だけ出す。0軒なら区画ごと出さない（埋めない）。
- エリア群・ジャンル・予算帯・条件の判定は、ハブの判定（`scripts/lib/area_genre_pages.js`）を使う。新しい基準は作らない。
- 「近い順」は使わない。店の緯度経度は今エリアの中心点で、5,004店に38通りしかない（3.3 節）。距離には最寄り駅（84.6%の店にある）と駅からの徒歩分を使う。
- 店舗ページは生成時に選んで HTML に書く（JS なしでも出る・検索エンジンからもたどれる）。クイックビューは同じ関数をトップに埋め込んで、その場で選ぶ（I-22 と同じく、生成時にトップへ埋め込む）。

### 7.5 読み込み中・失敗・空のとき

| 場面 | 出すもの |
|---|---|
| 全店のデータ（`data/stores.json`）の読み込み中 | ページの中に入っている店（今の `LOCAL_STORES`・TOP50）で先に一覧を出す。読み終わったら件数だけ更新し、見ている場所は動かさない（下に足すだけ） |
| 全店のデータの読み込みに失敗 | 「一部の店だけを表示しています［もう一度読み込む］」を一覧の上に出す |
| 写真の読み込みに失敗 | 写真の無い店と同じ表示（ジャンルの印）に切り替える。崩れた画像の印は出さない |
| 0軒 | W4 の「外すと増える条件」 |
| 保存が0件 | 「♡を押した店がここに並びます」と、話題店の列 |
| オフライン | 今の PWA の動きを変えない |

### 7.6 アクセシビリティ

- シート: `role="dialog"`・`aria-modal="true"`・題に `aria-labelledby`。開いたら題に焦点を移し、Esc で閉じる。
- チップ: `<button aria-pressed>`。色だけでなく ✓ でも状態を見せる。
- 下部タブ: `<nav aria-label="メインメニュー">`。
- 文字と背景のコントラストは 4.5:1 以上（小さい文字）。今のトークンの組み合わせは第3章で測った値を使う。
- 焦点の枠を消さない（`:focus-visible`）。
- `prefers-reduced-motion` のときは、シートの動きと横スクロールの慣性を止める。
- 写真の `alt` は店名（料理名が分かるときは料理名）。飾りのアイコンは `aria-hidden="true"`。
- 押せる範囲は 44px 四方以上。文字は 12px 以上、読む文字は 13px 以上（制約12）。

### 7.7 計測（GA4 のイベント）

- 今あるイベント名は変えない。名前を変えると、前後の比較ができなくなる。今の名前は次のとおり。
  - トップ: `search`・`sort_change`・`modal_open`（店名・ジャンル・エリア・source）・`fav_add`・`fav_remove`・`share_x`・`share_line`・`share_copy`・`outbound_click`・`cta_click`（`nbReserveExit` 経由）・`cta_call_click`・`cta_gmap_click`・`reel_play`・`feedback_open`・`feedback_submit`
  - 店舗ページ: `cta_click`（location=store_page）・`cta_call_click`・`cta_gmap_click`・`outbound_click`・`reserve_report_yes`/`no`
  - 特集: `feature_store_click`（店の値はリンク先のスラグ。I-08 で店名をやめた）・`cta_click`（location=feature）・`internal_link_click`
  - ジャーナル: `cta_reserve`（location=journal）。名前は違うが、予約送客の集計（`scripts/lib/reservation_exits.js` の `EXIT_EVENTS`）には入っている。名前はそろえない。店舗ページへのクリックは `journal_store_click`（store・journal。I-08 で新設。予約送客には混ぜない）
  - ハブ: `cta_click`（location=hub）。I-08 で `hub_store_click` から替えた
- 今のまま使うもの（足す値だけ決める）:
  - クイックビュー → `modal_open`。`source`（grid・ranking・trend_today・history・modal_reco・deeplink・unknown）は既にある。I-08 で `store_id` を足した（2026-10-11 に調べて確かめた。今までは店名だけで、店ごとの集計がしにくかった）。
  - 保存 → `fav_add`・`fav_remove`。`location` を足す。
- 直したもの（I-08・PR #471）:
  - ハブの「ホットペッパーで予約」は `hub_store_click` を送っていた。予約送客の集計に入らなかったため、ほかのページと同じ `cta_click`（location=hub）に変えた。ハブは build.yml が作り直した日から変わる。変えた日は、マージ後に `data/measurement_changes.json` へ書く。
  - 特集の `feature_store_click` は、947件のうち720件で店の値が店名だった。リンク先のスラグにそろえた。
- GA4 のカスタムディメンションは `store_name` と `link_domain` だけ登録済みで、`store_id`・`location`・`source`・`feature`・`hub`・`journal` は未登録。登録しないと GA4 の通常のレポートでは切り口にできず、登録した日からしか集まらない（P-240・オーナーの操作）。
- 足すのは、成功指標（第10章）を測るのに足りないものだけ。今ある名前と重ならないことは確かめた（2026-10-11）。

| 足す名前 | いつ送るか | 何に使うか |
|---|---|---|
| `filter_apply`（条件の数・件数） | 「◯軒を見る」を押したとき | 絞り込みの使われ方 |
| `zero_result`（条件） | 0軒になったとき | 0軒の率 |
| `related_click`（store_id・理由の種類） | 似た店を押したとき | 似た店の理由ごとの効き方 |

- 送る値に、個人を特定できる情報は入れない。
- オーナーの確認用の訪問は、今の `?nb_owner=1` の仕組みで内部の通信として分ける（`docs/ga4-internal-traffic-verification.md`）。

### 7.8 今ある機能の引き継ぎ

## 8. SEO 改善計画

### 8.1 変えないこと

- **URL は1本も変えない。** 店舗ページ `/stores/ID.html`・ハブ `/stores/area/…`・特集 `/features/….html`・ジャーナル `/journal/日付-slug.html`・トップ `/`。
  - 一覧・クイックビュー・保存は、トップ（`/`）の中の状態にする。canonical は `/` のまま。
  - ページ送りのための新しい URL も作らない（一覧ページは同じページの中で折りたたむ。W11）。
- canonical（自分を指す）・sitemap の生成・誘導ページ（古い ID → 今の ID）・noindex の決まり（ハブの閾値割れ・privacy）は今のまま使う。
- 構造化データで「出さない」と決めたもの（SearchAction・aggregateRating。`docs/decisions/0009`・`tests/structured_data_policy.test.js`）は戻さない。
- 本文・店の情報・リンクは、JS が無くても HTML に入っている状態を保つ。シートや折りたたみで隠すものも、HTML には残す（`<details>` か、CSS で隠して JS で開く）。

### 8.2 内部リンク（ページのつながり）

**階層**: トップ → エリア → エリア×ジャンル → エリア×ジャンル×条件 → 店舗ページ。見えるパンくずと `BreadcrumbList` を、この階層でそろえる。

| ページ | 出すリンク | 今との違い |
|---|---|---|
| 店舗ページ | パンくず（エリア・エリア×ジャンルのハブ）／似た店（7.4 節・最大6軒・理由つき）／もっと探す（その店が当てはまる条件のハブ）／この店が載っている特集・記事 | 似た店の選び方を1つにそろえ、同じ店にリンクが集まらないようにする（U-35）。**ジャーナルへのリンクを足す**（今は 0/5,001。U-46） |
| ハブ | 店のカード → 店舗ページ／条件のチップ → 条件のハブ（active のものだけ）／近くのエリアの同じジャンル／同じエリアのほかのジャンル／この条件の特集 | 写真つきのカードにする。31軒目以降も HTML に残す |
| 特集 | 店のカード → 店舗ページ・予約／掲載店のハブ／関連する特集 | 生成の3本（`gen_industry_features.js`）にも店舗ページへのリンクを入れる。ハブへのリンクを全特集に（今は 17/68） |
| ジャーナル | この記事の店 → 店舗ページ（計測つき）／合わせて読む（特集）／同じエリア・ジャンルの記事／ハブ | 店のカードを共通の部品にし、店舗ページへのクリックを計測する（今は 167本が計測なし） |
| トップ | エリア・シーンのチップ → 一覧かハブ／話題店・新しく載った店 → クイックビュー（`<a href>` は店舗ページ）／全店の索引 | 全店の索引は残す（クロールの入口）。手動で載せた店149店も入れる（U-68）。軽くする方法は 8.6 節 |

- 「もっと見る」ではなく、行き先が分かるリンク文にする（例「栄の焼肉 32軒」）。
- 店と特集・記事の対応表（どの店がどの特集・記事に載っているか）を生成時に作り、店舗ページの「載っている特集・記事」と、特集・記事の店のカードの両方で使う。今は特集・ジャーナルの側からしかたどれない。

| ページ | 型 | 直すこと |
|---|---|---|

### 8.4 title・説明文・OG 画像

- **title と説明文から、人が全店を選んだと読める言い方を外す**（5.5 節）。掲載店の数は生成時にデータから入れる（U-08）。
- 変える順番（検索の順位を落とさないため）:
  1. 新しく作るページ（日次ジャーナル・新しい特集）は、その日から新しい言い方にする。
  2. 説明文（meta description）・OG・本文の署名・フッター（title 以外）を全ページで変える。
  3. title に「業界人」などを含むページ（ジャーナル57本・特集約30本）は、GSC の表示が多い順に分けて変え、28日ごとに前後を比べる。
  - ジャーナルの題の実験で書き換えた15本（`data/journal_title_experiment.json`）は、題の前30字の規則と `og:title` の形を保つ（`tests/journal_title_front.test.js`）。
- OG 画像:
  - 店舗ページは、HotPepper の写真の URL をそのまま使う（今は wsrv.nl 経由。U-57）。写真の無い店は、サイト共通の OG 画像（1200×630 の PNG）にする。
  - 特集・ジャーナルでアイコンのままの39ページは、掲載店の写真にする（U-66）。

### 8.6 速さ（Core Web Vitals）

速さは順位の要因の1つで、何より使い勝手に効く。第3章の測定で大きいものから直す。

| 順 | すること | 効く所 | 見込み |
|---|---|---|---|
| 1 | Web フォントをやめる（5.3 節の案A） | 全ページ | 通信量がページあたり 0.8〜2.0MB 減る【確認済みの量】。ハブの CLS が下がる【推測】 |
| 2 | 写真に幅と高さ・最初の写真の優先度・遅延読み込みの見直し | 店舗・特集・ジャーナル | ジャーナルの CLS（0.129・10周すべてで 0.1 超）が下がる【推測】。店舗ページの LCP（初めて見られる店で中央値 7.0s）は、待ちの大半が写真の配信元（画像変換サービス）なので、この項目だけでは下がらない見込み【推測】。配信元の判断（4.4 節 #3・U-84）と合わせて決める |

### 9.2 この順番にする理由

- **I-01 を最初にする。** テストが赤のままだと、ほかの変更で壊したことに気づけない。
- **I-02・I-08 を、見た目を変える前にする。** 変えた後では「前」の値が取れない。
- **I-03（言い方）を、テンプレートを作り直す I-14・I-29・I-30 より前にする。** 後にすると、同じテンプレートを2回直すことになる。言い方は P0 でもある。
- **I-12・I-26（フォントと色の土台）を、部品の作り直し（I-14・I-19・I-28）より前にする。** 部品の大きさと色はトークンで決まるため。
- **I-09〜I-11（写真）を、カードと店舗ページより前にする。** 写真の大きさ・比率・撮影者の欄が決まらないと、部品の形が決まらない。
- **店舗ページ（段階2）を、トップ（段階3）より前にする。** 検索から来る人のほとんどは店舗ページに着く（3.10 節）。
- **I-15・I-16 の判定を、I-22（クイックビュー）と I-28（ハブ）が使い回す。** だから段階2で先に作る。
- **I-21（URL と戻る）を、I-22（クイックビュー）より前にする。** クイックビューは履歴の扱いに乗る。
- **I-27（下部タブ）を、ページの部品が決まった後にする。** 骨組みを先に変えると、部品の変更のたびに作り直す。
- **title の変更は分けて出す。** I-03 の title と I-18 は、GSC の表示の多い順に分けて出し、28日ごとに前後を比べる（8.4 節）。ジャーナルの題の実験の15本は、2026-11-06 まで変えない。

1. 作業ブランチで直す。生成器を直したときは、生成し直したページの数と、変わったページの見本を差分で見る。
2. `npm test`・`node scripts/audit_design_system.js --check`・`node scripts/audit_inline_js_syntax.js --check`・その変更に関係する監査を通す。

6. main に入れたら、次の日次の処理（`build.yml`・日次ジャーナル・`daily-trending5.yml`）が通るのを見届ける。
7. 第10章の指標を、決めた日数の後に比べる。

### 9.5 元に戻す方法

- 改善案ごとに1つのプルリクエストにするので、そのマージを取り消せば戻る（`git revert`。force push と reset は使わない）。
- 生成するページ（店舗ページ・ハブ・特集の一部・ジャーナルの一覧）は、生成器を戻せば、次の `build.yml` で元の形に作り直される。急ぐときは手元で生成器を回してコミットする。
- `apply_*` で全ページに当てた変更（共通クローム・デザインシステム）は、ライブラリとページを同じコミットに入れる。戻すときも一緒に戻る。
- 戻しても元に戻らないものがある。先に知っておく。
  - **title と URL の評価**: 検索エンジンが読み直すまで時間がかかる。だから title は分けて出す（9.2 節）。URL は変えない（8.1 節）。
  - **計測**: 変えた日と戻した日を `data/measurement_changes.json` に書く。書かないと前後の比較が壊れる。
  - **利用者の端末に残るもの**: 保存などのキーと中身の形を変えないので、戻しても消えない。Service Worker を変えたときは、古いキャッシュが残る期間を考える（この計画では変えない）。
  - **日次ジャーナル**: テンプレートを戻したら、その日の記事が新旧どちらの形で出たかを確かめる。

### 9.6 毎日の自動処理との関係

- `build.yml`（毎日）が店舗ページ・ハブ・特集の一部を作り直す。生成器を変えた日の次の実行で、全ページに反映される。
- 日次ジャーナルは Mac の launchd で無人で動く。テンプレートや生成器を変えたら、次の1本が公開されるまで見届ける。止まったら `journal-watchdog.yml` が Issue を出す。
- `daily-trending5.yml`（毎朝）は写真の URL を書き換える（I-10 で直す）。
- 特集の掲載店の入れ替えは月に1回（`refresh_feature_rosters.js --if-stale`）。テンプレートを変えた月は、入れ替えの後の形も確かめる。
- 定期ルーチンのプルリクエストは自動でマージされる（`routine-pr-automerge.yml`）。改修のプルリクエストとぶつかったら、改修の側で取り込み直す。

## 10. 検証方法と成功指標

### 10.1 考え方

- 依頼の5つの観点（操作性・回遊性・滞在時間・SEO・コンバージョン）を、それぞれ1つ以上の数字で測る。
- 1つの数字だけでは判定しない。
  - 滞在時間と回遊は、操作が増えただけでも伸びる。
  - なので、必ず「目的を果たせたか」（予約先へのクリック・保存）と「迷っていないか」（0軒の率・操作の数）と一緒に読む。
  - 滞在時間だけが伸びて、予約先へのクリックや保存が伸びない変更は、成功と数えない。
- 目標の値は、基線の分布を測ってから決める（品質ゲート原則5）。この文書では向きと、悪くなってはいけない線（ガードレール）だけを決める。
- 店舗ページの GA4 は 2026-05-08〜10-09 に止まっていた（SEO-115）。店舗ページを含む GA4 の数字は、10-09 以降のデータで基線を取り直してから比べる（SEO-118）。

**数字の取り方（どの指標にも共通）**

1. 期間: 変更を main に入れた日を D とする。前は D-28〜D-1、後は D+1〜D+28 の28日ずつで、D は数えない。28日にするのは曜日の並びをそろえるため。
2. 店舗ページを含む GA4 の数字は、2026-10-09 以降のデータだけを使う（10.1 節）。前の期間がそこまでさかのぼれないときは、取れる日数で前後の長さをそろえ、そのことを書く。
3. 区切り: 端末（スマホ・PC）と、ページの種類（トップ・店舗ページ・ハブ・特集・ジャーナル。URL の先頭で分ける）ごとに出す。合計だけで判定しない。
4. 重なり: 同じ期間に、指標に響く別の変更（9.4 節。改善案は1つずつ出す）や、`data/seasonal_events.json` の行事（年末の宴会など）が入ったら、そのことを記録に書く。
5. 自分の閲覧: オーナーと作業者は、確かめる端末で先に `?nb_owner=1` を開く。その端末は独自のイベント（`cta_click` など）を送らないが、訪問（セッション）は GA4 に入る。GA4 のデータフィルタ「内部トラフィック」が「有効」でない間は、率の分母に混ざる（`docs/ga4-internal-traffic-verification.md`）。基線を取る前にフィルタの状態を記録し、前後で同じ状態にする。
6. 件数が少ない指標: どちらかの期間で分子の件数が30件未満なら、向きを判定せず「保留」と書き、期間を56日に延ばす。予約送客は直近30日で55件（2026-10-10 の `data/store_referrals.json`）なので、端末やページの種類で分けると30件を下回りやすい。30件は仮の値で、I-02 で基線の分布を見て直す（品質ゲート原則5）。
7. 記録: 数字と一緒に、期間・区切り・使ったイベント名・取った日を残す。GA4 の数字は、決まった期間で取り直せるスクリプトで取る（I-02 で作った `scripts/ga4_baseline.js`。実行は `.github/workflows/ga4-baseline.yml`）。
8. 速さ（実測）: 測定機の電源（と低電力モード）をそろえる。基線は電源ごとに別のファイルで持ち、前後は同じ日・同じ電源の組で比べる。バッテリー駆動の値と充電器の値を比べない（`docs/decisions/0018-speed-comparison-same-day-same-power.md`）。店舗ページの LCP は、店を替えて測った値（`store-sample`）で比べる。前と後で別の店を無作為に選ぶ（`docs/decisions/0019-store-page-speed-measured-across-stores.md`）。

### 10.4 操作の数を測るタスク

- 前と後を同じ日に、手元の配信で測る。前は変更を入れる直前の main、後はそのプルリクエストの最後のコミット。どちらも付録A の手順で配信する。データ（`data/`）は、そのプルリクエストが変えたもの以外は同じなので、日ごとに変わる「今日の話題店」なども前後でそろう。
- 端末: 390×844（スマホ）と 1280×800（PC）。`capture.js` と同じ大きさ。

- 達成（終わりの条件を満たした）か未達かを記録する。始める所をそろえられないタスクは比べず、理由を書く（10.6 節の Codex の条件）。

## 付録A 再現の手順

この文書の画面・速さ・数字は、次のスクリプトで同じ条件のまま取り直せる。どれもリポジトリの直下で実行する。puppeteer はリポジトリの `node_modules` にあるものを使う（新しい依存は足していない）。

| 何を | コマンド | 対応する節 |
|---|---|---|
| 画面を撮る | `node docs/qa/uiux-2026-10/capture.js <出力先> [topMobile topDesktop searchAndModal filterPanel pages]` | 2.1 節・第3章 |
| 表示の速さを測る | `node docs/qa/uiux-2026-10/perf.js 10 > runs.jsonl` → `node docs/qa/uiux-2026-10/perf_summary.js runs.jsonl --label … --date … --note … --out …`（10周。`ONLY=top,hub` で絞れる。バッテリー駆動なら警告） | 2.2 節・3.6 節・第10章 |
| 主な数字を数え直す | `node docs/qa/uiux-2026-10/counts.js` | U-01・U-31・U-32・U-33・U-35・U-36・U-71・U-73・U-83・5.6 節・7.3 節 |

- `capture.js` と `perf.js` は、何もしなければ本番（https://nagoya-bites.com/）を開く。GA4 などの計測への通信は止めてある。
- 手元のファイルで撮るときは、別の端末で `python3 -m http.server 8766 --bind 127.0.0.1` を動かし、`BASE=http://127.0.0.1:8766` を付けて実行する。
- 速さは揺れる（特に TBT とハブの CLS は、測定機の電源で割れる）。前後を比べるときは、同じ日に、同じ電源（標準は充電器）で10周測り、中央値・最小〜最大・目標超の回数を見る。測る間は画面を起こしておく（`(caffeinate -u -d -i -t 秒 &)`。画面が消えると描画されない回が出る。描画されなかった回は集計が無効として数える）。
- `counts.js` は外部へ何も送らない。`data/stores.json` と生成されたページを読むだけ。
