# 0019 店舗ページの速さは、同じ店を測り続けず、店を替えて測った値を基線にする

- 日付: 2026-10-11
- 状態: 採用
- 関連: Linear P-241（I-02）・P-235（親）/ backlog DSN-013 / `docs/uiux-overhaul-plan-2026-10.md`（3.6 節 U-84・I-09・10.2 節・付録 A）/ I-02 の PR #472（claude/uiux-i02-baseline）/ 判断の記録 0018

## 背景

- 設計のときに測った店舗ページの LCP は 6.1s（1回）だった。I-02 で同じ店（J004660861）を10周測ると、中央値は 1.8s・最大 1.9s で、6.1s は再現しなかった。
- 店舗ページの写真は、画像変換サービス（wsrv.nl）を通して配信している（U-57）。写真の URL を直接取りに行くと、**初めて見られる店の写真は 2.9〜4.4s かかり、2回目以降は 0.07〜0.4s だった**（3店で確認）。変換サービスの側にキャッシュができるまで、元の画像の取得と変換を待つと見られる【推測】。
- 同じ店を10周すると、最初の1回でキャッシュができて、あとの回は速く出る。設計のときの 6.1s は、キャッシュが無い状態の値だった可能性が高い【推測】。
- sitemap.xml の店舗ページから無作為に10店を選び、1店ずつ測ると（`store-sample`）、LCP は中央値 7.0s・最小 2.1s・最大 7.5s で、10店のうち9店が目標（2.5s）を超えた。LCP の要素は10店ともヒーロー写真だった【確認済み】。
- HotPepper の配信元を直接取ると（4枚）、初回 0.2〜0.9s で、2回目に速くなる傾向は無かった。変換サービスのような初回の遅さは無い【確認済み】。
- 実際の訪問の大半が初めて見られる店かどうかは、まだ確かめていない。店舗ページは約4,850本あり、訪問は広く散るので、そうなる見込み【推測】。GA4 の店舗ページ別の表示数の分布で確かめられる。

## 決めたこと

1. 店舗ページの LCP の基線は、**店を替えて測った値**（`perf.js` の `store-sample`。sitemap.xml の店舗ページから無作為に選び、1周ごとに別の店）で持つ。同じ店を測り続ける `store` は、通信量・DOM・TBT などの比較と、キャッシュが効いた状態の参考値として残す。
2. **前と後で別の店を測る**。標本は毎回無作為に選び直し、測った URL は1行ごとの `url` に残す。同じ店を測り直すと、前の測定でキャッシュができていて、速く出る。約4,850本から10店を2回選んで重なる見込みは 0.02 店ほど。
3. 店舗ページの LCP を比べるときは、中央値のほかに、最小〜最大と目標（2.5s）を超えた店の数を見る（店ごとのばらつきが大きい）。
4. 写真の配信元を変えたとき（I-09 など）は、変える前後を、店を替えて測り直す。

## 選ばなかった案と理由

- **同じ店を測り続ける案**: キャッシュが効いて、初めて見られる店の遅さが見えない。基線が良く出すぎて、改修の前後を比べても差が出にくい。
- **測る前に写真を取っておく（キャッシュを温める）案**: 実際の訪問では、キャッシュが温まっていない店が多い見込み。それに、約4,850店ぶんを外部サービスへ先に取りに行くのは、相手への負担が大きい。
- **標本を固定する案（毎回同じ10店）**: 1回測ると、その10店はキャッシュができる。次に測るときは温まっているので、前と後を比べられない。
- **変換サービスを通さずに測る案**: いまの配信を測らないことになる。やめるかどうかは別の判断（4.4 節 #3・I-09・オーナー）。やめたあとに、この測り方で前後を比べる。
- **訪問数で重みを付けた標本にする案**: 店ごとの訪問数は GA4 の店舗ページ別の表示数が貯まってから決める。それまでは無作為で足りる（下の見直す条件）。

## 見直す条件

- GA4 の店舗ページ別の表示数から、訪問が特定の店に集中していて、多くの訪問でキャッシュが温まっているとわかったとき。その場合は、訪問数で重みを付けた標本に変える。
- 画像変換サービスをやめたとき（I-09）。キャッシュの効き方が変わるので、`store` と `store-sample` の差を測り直す。
- 標本10店のばらつきが大きくて、前後の差が読み取れないとき（店の数を増やす）。
