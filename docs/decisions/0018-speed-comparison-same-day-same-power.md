# 0018 速さの前後比較は「同じ日・同じ電源」で行い、基線は電源ごとに持つ

- 日付: 2026-10-11
- 状態: 採用
- 関連: Linear P-241（I-02）・P-235（親）・P-243（充電器での測り直し）/ backlog DSN-013 / `docs/uiux-overhaul-plan-2026-10.md`（2.2・3.6・10.2 節・付録 A）/ I-02 の PR #472（claude/uiux-i02-baseline）

## 背景

- 設計書の 10.2 節は、速さ（LCP・CLS・TBT・通信量）の前後比較を「同じ条件で5回測った中央値」で行うとしていた。条件は 2.2 節（スマホ相当・CPU 4倍遅く・遅延 150ms・下り 1.6Mbps・キャッシュなし）。
- 2026-10-11 の基線の測定で、**同じページ・同じ内容（HTML・DOM・通信量が同じ）なのに、TBT が数十 ms と数秒に割れた**。ハブの CLS も 0.013 と 0.652 に割れた。割れ方は周ごとにそろって現れ、1回限りの外れ値ではなかった。
- 端末の負荷では説明できなかった。Node 側の計算時間（hostBench）は一定のまま、Chrome の描画側の計算時間（`rendererBenchMs`）もバッテリー駆動の間は一定のまま、TBT だけが割れていた。
- macOS の電源の記録（`pmset -g log`）と、各行の測定時刻（開始時刻に、1行ごとの読み込み時間と待ち時間を足して推定）を突き合わせると、**割れ目が、Mac の電源が充電器からバッテリーに切り替わった時刻（20:57:31 JST）と一致した**。
  - 充電器のとき（TBT の中央値・暫定の7回）: トップ 53・特集 13・ハブ 159・特集一覧 6・ジャーナル一覧 1,169 ms。
  - バッテリー駆動のとき（TBT の中央値・10周）: トップ 861・特集 1,004・ハブ 2,137・特集一覧 1,406・ジャーナル一覧 3,509 ms。最小〜最大も、充電器の側とほとんど重ならない。
  - LCP は 0〜0.1s ほどの差、通信量・DOM は同じだった。
- 測定機の設定を調べると、**低電力モードが「バッテリー駆動のときだけ」入る設定**だった（`pmset -g custom`: Battery Power は `lowpowermode 1`・AC Power は `0`。Apple M5・性能コア4＋効率コア6）。電源が切り替わると低電力モードも一緒に切り替わるので、**TBT が割れた原因が電源そのものか低電力モードかは、今のデータでは区別できない**。低電力モードは CPU の動作を抑えるので有力な説明だが、確かめてはいない。
- ただし**時刻が一致しただけで、因果は確かめていない**。確かめるには、充電器をつないで測り直す（つなぐのはオーナー本人の操作）。さらに、充電器をつないだまま低電力モードを入れる、またはバッテリー駆動のまま切って測れば、電源と低電力モードを分けられる（システム設定の変更なのでオーナーの判断）。
- 設計書 3.6 節の TBT（トップ 0.7〜1.9s・ハブ 2.8〜2.9s など）は、バッテリー駆動（低電力モードが入った状態）のときの値だった。
- **訂正（2026-10-12）**: 上の「ハブの CLS も 0.013 と 0.652 に割れた」は、電源の違いではなかった。0.65 になる周の数は、2026-10-11 のバッテリー駆動で 7/10、充電器で 3/7、2026-10-12 のバッテリー駆動で 3/10 と、電源と並ばない。原因は Web フォント（Google Fonts）が届く順番で、パンくずの折り返しが変わるかどうか（`docs/uiux-overhaul-plan-2026-10.md` の U-53。同じ条件で Web フォントを止めると CLS は 0.000）。同じ日・同じ電源で比べる決め方は TBT について今も有効で、ハブの CLS は「0.1 を超えた周の数」で見る。また CLS の値は 2026-10-12 に web.dev の定義（いちばん大きいセッション窓）に直した。2026-10-11 の基線の CLS は全部のずれの合計なので、比べない。

## 決めたこと

1. 速さの前後比較は、**同じ日に、同じ電源（と低電力モード）で測った値どうし**で行う。状態が違う回どうしは比べない。
2. 基線は電源ごとに別のファイルで持つ（`docs/qa/uiux-2026-10/baseline/perf-2026-10-11-battery.json`・`perf-2026-10-11-ac.json`）。
3. `perf.js` は1回ごとに電源（`power`: ac / battery）と低電力モード（`lowPowerMode`: 1 入／0 切）を記録し、バッテリー駆動なら警告を出す。`perf_summary.js` は電源ごとの回数（`host.power`）・低電力モードの入り切りごとの回数（`host.lowPowerMode`）と、1回ごとの要点（`samples`）を出す。
   - 2026-10-11 のバッテリー側の基線には、1回ごとの低電力モードの記録が無い（記録を足す前に測った）。設定の上では入っていたはず、と `notes` に書いた。
4. 前後の比較に使う標準の状態は**充電器をつないだ状態**とする（この Mac では低電力モードも切れる）。バッテリー駆動で測った前後は、そう書いて、同じ日に同じ状態で測った組だけで比べる。
5. 設計書の 3.6 節・U-52〜U-54・10.2 節の速さの行・付録 A を、電源ごとの値と上の手順に直す。「5回の中央値」は「10周の中央値・最小〜最大・目標超の回数」にする（中央値だけでは割れたことが見えない）。
6. 充電器をつないで10周測り直し、充電器側の基線を1回ごとの電源の記録つきにする。やるのはオーナー本人（Linear: P-243）。それまで充電器側の基線は暫定とする（旧形式の35行と新形式の14行で、電源は測定のあとに `pmset -g log` で付けた）。

## 選ばなかった案と理由

- **端末の負荷の目安（Node の計算時間・`loadavg`・描画側の計算時間）で、そろった回だけ比べる案**: 測ってみると、目安は一定のまま TBT が割れた。目安として働かないので、比べる条件にならない。
- **割れた値を混ぜた中央値を基線にする案**: 中央値は割れ目を平らにして、どちらの状態にも当てはまらない値になる。改修の効果と電源の違いが区別できなくなる。
- **TBT を指標から外す案**: TBT は、操作に反応できない時間（長いタスク）を見る数少ない項目。状態をそろえれば使えるので、外さない。
- **バッテリー駆動を標準にする案**: 実際の利用者の端末は電池で動くものが多いが、測定機の電源管理の影響を受ける値と、サイトの重さの違いが区別できない。標準は電源管理の影響が小さいと見込まれる充電器の状態にし、それが本当かは取り直しで確かめる。
- **測定のたびに測定機の設定（低電力モード）を書き換える案**: 測定機の設定を変えるのはオーナーの判断で、元に戻し忘れる危険もある。設定は変えず、状態を記録して比べる。
- **電源に関係なく、今ある行をそのまま基線にする案**: 状態が混ざった中央値は、再現も比較もできない。

## 見直す条件

- 充電器をつないで測り直した結果、電源で TBT が割れないとわかったとき（原因が電源でも低電力モードでもなく、時間帯や他の作業だったとき）は、この決めを外し、原因に合わせて書き直す。
- 原因が低電力モードだと分かったとき（バッテリー駆動のまま低電力モードを切ると割れ目が消える、など）は、標準を「低電力モードが切れている状態」と言い換える（充電器でなくてもよくなる）。
- CI の実行環境など、電源の影響が無い環境で前後を測る方法ができたとき（その環境の値を標準にする）。
- LCP・通信量・DOM が電源で変わると確かめられたとき（今回の測定ではほぼ同じだった）は、比べる前提をさらにそろえる。
