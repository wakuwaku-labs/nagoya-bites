# 0020 統合で残すレコードは、前回の記録で残した側を最優先にする

- 日付: 2026-10-12
- 状態: 採用
- 関連: Linear P-265（親 P-263）/ ISSUE-132 / `scripts/lib/store_dedup.js` / `data/store_merge_pairs.json` / `build.js`

## 背景
- 同じ店の重複レコードを build.js が統合するとき、残すレコードを「非空項目の数 → 編集部レコード → ホットペッパーIDを持つか → 元の配列の順」で選んでいた（`pickBase`）。
- 統合の記録（`data/store_merge_pairs.json`）の履歴を追うと、残す側が前回と逆になった回がある。記録のあった9回のうち、2026-10-06（1組）・10-09（3組）・10-11（4組）の3回、のべ8組。10-11 の4組は、肉ト魚 大衆酒場 ひとめぼれ 名駅3丁目店・BeTogetherBeTogether 今夜Bar・シャンタムール・YOHAKU COFFEE 今池。
- 入れ替わると、`stores/<ID>.html` の現役ページと誘導ページ（canonical で相手を指す軽量ページ）が入れ替わる。検索エンジンから見た canonical の向きが逆になる。オーナー確認済みの組（店名が違う）では、画面に出る店名まで入れ替わる（例: シャンタムール／シャンタムール サウス）。
- 入れ替わった日は、トップの全店舗一覧が誘導ページを指したまま main に入った（P-264 で一覧の作り直しを足して止めた）。入れ替わること自体を止めるのがこの記録。
- 原因を確かめるため、入れ替わった4組を data/stores.json の実レコード（入れ替わる前の版と後の版）で再現した。入れ替わった日の入力そのものは再現できていない。
  - 3組は、元の配列の順を逆にすると、残る側も逆になる。項目数が並ぶと最後の決め手が元の配列の順になり、その順はホットペッパーの並びに左右される［推測］
  - 1組（シャンタムール）は、並びを替えても今のレコードでは同じ側（J000015669）が残る。以前は逆側が残っていたので、並び以外（項目数の変化。写真・評価の取得の成否など）が働いたと考えられる［推測］
  - つまり並びの揺れだけを直しても足りず、項目数より先に前回の記録を見る必要がある

## 決めたこと
- 前回の統合の記録（`data/store_merge_pairs.json` の `merged[].kept`）にあるレコードが、今回の同じ組にもいれば、項目数などより先に、そのレコードを残す。照合は `ホットペッパーID` か `slug`（ID の無いレコードは slug）。
- 記録に無い組（初回・新しい組）、記録が読めない、記録の側が組にいないときは、今までと同じ決め方で残す。
- 残すレコードが決まったあとの統合は変えない（足りない項目は相手から補う・編集部の項目は落とさない）。残す側の項目が相手より少なくても、相手の項目で補われる。
- build.js が統合の前に記録を読む（この後で同じファイルを書き換えるため）。読めなくてもビルドは止めない（空の記録として扱う）。
- この記録を入れた時点の向きは、2026-10-11 21:44（UTC）の自動ビルドで書かれた記録のとおりになる（現役の店舗ページもその向き）。

## 選ばなかった案と理由
- 最後の決め手を ID の昇順などに替える: 今の向きと逆になる組が出て、導入した日にもう一度入れ替わる。項目数の変化による入れ替わりも止まらない。
- 現役の店舗ページがあるほうを残す（`stores/*.html` を見る）: ビルドの途中のページの状態に依存する。順序の問題（P-264）がもう一度入り込む。記録は決定的に読める。
- 入れ替わりを許し、周りを追いつかせる（P-264 の作り直しだけで済ませる）: 一覧は直るが、URL（現役か誘導か）と画面の店名が日ごとに揺れるのは残る。

## 見直す条件
- 残す側を意図して替えたいとき（店名を替えたい・古い ID をやめたい）: `data/store_merge_pairs.json` の該当の組の `kept` の `ホットペッパーID` と `slug` を、残したい側のものに書き換えてコミットする。次のビルドからその側が残る。
- 記録が古くなって困る例が出たとき（残している側のデータが長く薄いまま、など）。
- ホットペッパーの ID が付け替わる運用に変わったとき（記録の ID が組にいなくなるので、既定の決め方に戻る。その日だけ向きが変わりうる）。
