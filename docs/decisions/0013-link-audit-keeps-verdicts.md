# 0013 日次のリンク照合は、取得できなかった回に前の判定を消さず、食べログが止まったら専用の Issue で1回だけ知らせる

- 日付: 2026-10-09
- 状態: 採用
- 関連: Linear P-167（ISSUE-163）・P-168（ISSUE-164）・P-166（ISSUE-162）・P-162（ISSUE-158・親）/ `scripts/audit_store_link_identity.js`・`.github/workflows/link-audit-watchdog.yml`・`scripts/nightly_qa.js`（link-audit-health）・`tests/audit_store_link_identity.test.js`

## 背景
- build.yml は毎日 `audit_store_link_identity.js --scope all --limit 60` で、店舗の食べログ・ホットペッパーのリンクがその店のページを指しているかを照合する。結果は照合キャッシュ `data/store_link_identity_checked.json` に残り、別の支店の監査（`audit_tabelog_branch_mismatch.js`）と特集・ジャーナルの監査（`audit_page_store_links.js`）がその記録を読む。
- 食べログは遅くとも 2026-10-05 から、CI の取得に HTTP 403 を返す（10-05 は11件、10-06 は5件、10-09 は53件。すべて 403）。10-09 には手元の Mac からも 403 だった。食べログの照合で最後に取得できたのは 09-20。
- 旧実装の問題:
  - 取得できなかった結果（fetch-error）で、前の判定を上書きしていた。上書きされると題名と住所の記録が消え、二つの監査がその組を数えなくなる（偽の緑）。09-20 の一致が60日を過ぎる 11-19 から、毎日上書きが起きるはずだった。
  - 照合の順番は店の並び順だった。そのため、取得できない組と不一致の組が毎日60件の枠を先に使い、一度も照合していない食べログのリンク20件には回らなかった。
  - `--check` は、取得できなかった組も不一致に数えていた。そのため毎日赤く、赤が意味を持たなかった。
  - 403 が続いても60件すべてを試していた。
  - ホットペッパーの題名に「＜ネット予約可＞」が付く店は、店名を読めず、正しいリンク7件を不一致と数えていた（ISSUE-162）。

## 決めたこと
- **取得できなかった照合は、前の判定を消さない。**
  - 前の判定は、一致・別の店・閉店・支店違い・ページが無いのいずれか。
  - 取得できなかった照合とは、HTTP 404/410 以外の fetch-error と no-title。
  - その回は、試した日時・理由・エラーだけを足す（`lastAttemptAt`・`lastAttemptReason`・`lastAttemptError`）。
  - HTTP 404/410 は「ページが無い」という判定として扱い、前の判定を置き換える。消えたページへのリンクを、一致のまま残さない。
- **照合の順番。**
  - 種類は食べログが先。別の店を指すリンクが実際に見つかってきたのは食べログ。ホットペッパーのリンクは、ほとんどが HotPepper の API の店そのもの。
  - 同じ種類の中では、一度も照合していない組が先。その後は、最後に試した日が古い順。
  - 判定が出た組は、60日たつまで照合し直さない。
  - 取得できなかった組は、最後に試してから7日あける。
- **同じ種類で取得の失敗が5件続いたら、その回のその種類はやめる。** 断られている間は取得を続けない。残りの枠はホットペッパーに回る。
- **403 は回避しない。** 別の IP・別の取得手段・UA の偽装はしない。手元から試し、断られたら日を改める。
- **`--check` が exit 1 にするのは、判定の出ている不一致だけ。** 報告 `data/store_link_identity_report.json` は、次の4つを分けて出す。
  - 不一致（`mismatches`）
  - 取得できたことが無い組（`unfetched`）
  - その回に試した件数と、取得できた件数（`run`）
  - 種類ごとの状況（`health`）: リンク数・一度も照合していない件数・取得できたことが無い件数・最後に取得できた日
- **食べログを最後に取得できた日が30日より前なら、外へ知らせる。**
  - 判定は照合キャッシュの記録だけで行う。判定が出た照合の時刻の最大を使い、取得できなかった回はこの時刻を進められない（制約10）。CLI は `--health`（`--json`）。
  - 夜間QA には soft で載せる（link-audit-health）。
  - 外へ知らせるのは、専用の監視 `.github/workflows/link-audit-watchdog.yml`（毎日 16:30 JST）。GitHub Issue を1件だけ開く（＝オーナーにメール）。
  - 続いている間は本文を書き換えるだけにする。コメントは付けず、ジョブも失敗にしないので、毎日メールは届かない。
  - 取得できたら自動で閉じる。Issue には、原因（403）・一度も照合していない件数・手元で照合し直すコマンドを載せる。

## 選ばなかった案と理由
- **夜間QA の soft だけにする案:** レポートに残るだけで、人が見に行かないと分からない。制約11と「『気づけるはず』を検知と数えない」に反する。
- **夜間QA の hard にする案:** 原因が外部で長く続く。そのため「🔴 夜間QA FAIL」の Issue が開いたままになり、他の hard の失敗が埋もれる。
- **既存の監視と同じく、毎日コメントしてジョブを失敗にする案:** 原因は外部で、コードでは直せない。毎日メールを送ると、届いても何もできない知らせが続き、無視されるようになる（ISSUE-084 原則6）。知らせるのは止まったときと戻ったときの2回にする。
- **取得できなかった結果も判定として記録し続ける案（旧実装）:** 記録が消え、監査が数えなくなる。問題が減ったように見える。
- **ホットペッパーを手動キュレーション店だけに絞る案:** 手動キュレーション店でホットペッパーIDを持つのは1件だけ。ホットペッパーの照合は CI から取得できており、ID の入力違いや閉店（404）を拾える。順番を食べログの後にすれば十分。
- **食べログへの取得を別の経路（別の IP・ヘッドレスブラウザ・UA の偽装）で通す案:** 相手が断っている取得を続けることになる。採らない。

## 見直す条件
- 食べログが CI から再び取得できるようになったとき。止める件数（5件）と、試し直すまでの日数（7日）は、そのときの成功率で見直す。
- 403 が 2026-11-19 を過ぎても続いたとき。この日に 09-20 の一致がすべて60日を過ぎる。手元からも取得できなければ、照合の記録が古いことを、店舗ページのリンクを残すかどうかの判断に使うかを決める。
- ホットペッパーの照合で、判定の出た不一致が見つかるようになったとき。順番の優先を見直す。
