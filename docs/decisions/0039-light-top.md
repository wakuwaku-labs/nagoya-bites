# 0039 トップの「全店の索引」を、エリア別の一覧ページへのリンクに置き換える（トップは約半分の重さに・店舗ページまでは 1 回から 2 回・ItemList は 1 本）

- 日付: 2026-10-14
- 状態: 採用
- 関連: Linear P-403（親 P-235・UI・UX全面改修・計画の I-25）/ 判断の記録 0021（掲載店数の書き方）・0029（トップの構造化データ）・0036（カードの店舗ページへのリンク）/ `scripts/inject_store_links.js` / `scripts/audit_store_reachability.js` / `tests/top_light_index.test.js` / `tests/audit_store_reachability.test.js` / `tests/index_card_compact.test.js` / `tests/selection_wording_sources.test.js` / `data/page_weight_policy.json`

## 背景
- オーナーの決定（計画の #7・2026-10-13）: 全店の索引は、エリア別の一覧ページへのリンクに置き換える（案 1）。置き換えの前後で、検索の数字を同じ道具で比べる。
- トップの `index.html` は 1,324,788 バイト（gzip 299,484）。その 54% にあたる 717,870 バイトが、閉じたまま置かれた「エリア別 全店舗一覧」（STORE-INDEX）だった。中身は店舗ページへのリンク 4,848 本・検索へのディープリンク 157 本・エリアの開閉 84 個。画面ではほとんど開かれないのに、最初の描画の前に全部読み込まれる。
- トップの構造化データの ItemList は最大 3 本あった。静的な 1 本（`about`）は `numberOfItems` に 5,000 と書きながら中身は 3 件で、URL は店舗ページではなく `#genre=…` などの絞り込みだった。JS が店の読み込みごとに足す 2 本（50 件・80 件。URL は外部の予約サイト）は、読み込み中に増える（約 26KB・約 42KB）。
- 0036 のカードの店舗ページへのリンク（`nbStoreHref`）は、STORE-INDEX の「店名（エリア・ジャンル）→ href」から引いていた。索引をなくすと、カードのリンクが全店で消える。0036 の「見直す条件」が、この対応を別の形で渡すことを求めていた。
- 計画の注意: 全店の索引を軽くするときは、クロールの入口（検索エンジンが店舗ページへたどる道）を減らさないこと。

## 決めたこと
1. **索引は、エリア別の一覧ページ 101 本へのリンクに置き換える。** 見出しは「エリア別 店舗一覧」（フッターの同名のリンクと同じ語。旧「エリア別 全店舗一覧（N店）」から「全」と数を外した）、導入文は「エリアをタップすると、ジャンル別の店舗一覧ページへのリンクが開きます。」。エリア 10 群が閉じた `<details>`（見出しに「N軒」）で、開くと「{エリア}の飲食店（N軒）」と、店の多い順の「{エリア}の{ジャンル}（N軒）」が並ぶ。末尾に既存の「エリア×ジャンルをすべて見る →」。
   - 載せるのは、`data/area_genre_pages_manifest.json` で active、かつファイルが実在するページだけ（死にリンクを作らない）。リンク文は着地ページの見出し（h1）と同じ書き方に合わせ、件数は割れないよう 1 つの塊にした。リンクは 1 本ずつ高さ 44px 以上・文字 13px 以上。
   - ハブが 1 つも読めない日（manifest が無いなど）は、前の区画を残して警告する（空の区画で入口を消さない）。SCENE-INDEX（シーン別）は変えない（再生成してバイト同一）。
2. **載せるのは条件のハブを除く 101 本（エリアの一覧 1・エリア 10・エリア×ジャンル 90）にする。** 条件のハブ（個室・飲み放題など 593 本）まで足した 694 本をリンクしても、店舗ページの深さの分布も着けない店の数も 1 本も変わらなかった（読み取りだけの実験）。リンクを増やしても入口は増えず、トップが長くなるだけ。
3. **店舗ページまでの道は 1 回から 2 回になり、245 店（掲載中の 5.05%）にはトップからのリンクで着けなくなる。これを正直に記録し、安全網は今回は足さない。**

   | 掲載中の店の現役の店舗ページ 4,848 本 | 1 回 | 2 回 | 3 回 | 4 回 | 着けない |
   |---|---|---|---|---|---|
   | 前（索引が店舗ページへ直接リンク） | 4,848 | 0 | 0 | 0 | 0 |
   | 後（トップ → 一覧ページ → 店舗ページ） | 0 | 4,511 | 60 | 32 | 245 |

   - 数えたのは、公開ページの `<a href>` をトップから幅優先でたどった回数（JSON-LD・サイトマップは数えない）。誘導ページ（古い ID の軽いページ）は数えない。`node scripts/audit_store_reachability.js`（`--list` で着けない店の一覧、`--top-file` でトップだけ別の版にして前後を同じ道具で比べる）。
   - 着けない 245 店の内訳（`data/stores.json` と一覧ページの作り方から分類）: **エリア×ジャンルの店が 10 軒（`hubMinStores`）に満たず、ジャンル別の一覧ページが作られない組の店が 213**、休業・閉業の表示があり一覧ページが載せない店が 24、エリアが 10 群に入らない店が 4、ジャンルが 17 に入らない店が 4。エリアの一覧ページはジャンルのグリッドと統計だけで店へはリンクしないため、ジャンル別の一覧ページが無い店は、一覧ページ経由では着けない。うち 39 店は、他のどのページからもリンクされていない（トップの索引だけがリンクしていた）。残る 206 店は、同じく着けない店の「似た店」のリンクからだけ。
   - サイトマップには全店が残る（`<loc>` 5,931 本のうち、店舗ページ 5,005・ハブ 694・特集 69・ジャーナル 160。この変更はサイトマップを変えない）。つまり検索エンジンが店の存在を知る道は残り、内部リンクでの到達だけが細くなる。
   - ハブへの道は近づく: 前は深さ 1 が 18・深さ 2 が 217・深さ 3 が 459 → 後は深さ 1 が 101・深さ 2 が 593（どちらも、店数が基準に届かず noindex にした 13 本は着けない）。
   - 安全網は今回は足さない。根本の対策は、**エリアの一覧ページに「ジャンル別の一覧ページが無い店」のリンクを載せること**（上の 213＋4 の 217 店が対象。休業・閉業の 24 店は一覧ページに載せない今の方針のまま、エリアが 10 群に入らない 4 店は一覧ページが無いため残る）。一覧の生成器（`scripts/gen_area_genre_pages.js`）の変更で、計画の I-28（ハブを作り直す）と同じ場所になるので、この PR の範囲（トップの索引・店のカードのリンク）には含めない。トップに足す案（入口の無い 39 店に、貪欲に選んだ 41 店を足した約 80 リンク・約 8KB で、全 245 店に着ける見積もり）は、毎日変わる生成物から入口を計算すると区画が不安定になり、複雑さも増えるので足さない。オーナーの決定は「置き換えて前後を比べる」。先に置き換えの影響を数字で測り、出たら足す（「見直す条件」）。
4. **カードの店舗ページへのリンク（`nbStoreHref`）は、店のデータの ID（ホットペッパーID）から組み立てる。** `stores/<ID>.html`。例外だけを `var NB_STORE_PAGES = {"none":{…},"to":{…}}` に書く（`none` は ID があってもページが無い店、`to` は古い ID の誘導ページから移り先の現役ページがある店）。今日は両方とも空（掲載中の 4,848 店はすべて自分の ID のページを持つ）。
   - 表は STORE-INDEX の区画の末尾に置く。`var LOCAL_STORES` より前なので、最初の描画から全店のカードにリンクが付く（テストが順序を見る）。
   - ID が無い店（手動店 157）は、従来どおりリンクを付けずボタン（`role="button"`）のまま。手動店のページのスラグは英語名や店名から作られ、重なると接尾（`-2`）が付く（`gen-store-pages.js` の `toSlug`）ため、ブラウザ側で同じ結果を出すのは自明でない。別の課題にする。ID に英数字・`_`・`-` 以外の文字があるときも、リンクにしない。
   - 以前は「店名（エリア・ジャンル）」で引いていたため、同じ表記の店が 2 件あると曖昧でボタンに落ちていた。ID から組み立てると、同名でも ID が違えば各店にリンクが付く（今のデータには同じ表記の組が無く、リンクが付く店は 4,848 のまま）。
5. **ItemList は構造化データ全体で 1 本にする。** `<head>` の STORE-ITEMLIST の区画に生成して置き、静的な `about` の ItemList と JS の動的生成（`injectDynamicJsonLd`）はやめる。中身は `data/stores.json` の順で、現役の店舗ページに解決できる最初の 50 件（誘導ページと、検索へのリンクだけの店は載せない。移り先の現役ページがあれば移り先の URL。同じページは 1 回だけ）。URL は `https://nagoya-bites.com/stores/<ID>.html`、`numberOfItems` は件数と一致する。順はトップの最初の描画に使う先頭 50 件と同じ。0029 の「画面に見える事実だけ」に沿う。
6. **なくなるもの。** エリアを開いてその場で店のカードを出す展開・サブエリアの絞り込み・「このエリアを検索結果で見る」は無くなる（決定 #7 の範囲。エリアでの絞り込みは計画の I-20）。
7. **後始末として残すもの。** `buildCardHtml(r, 'index')` と `nbCardSizes('index')` の枝は、呼び出し元がなくなったが残す。同じ関数を、並行して進む計画の I-22 などが書き換える見込みで、ここで触ると競合する。カードを整理する次の課題で外す。`loadStores` の末尾から索引の 2 行（`injectDynamicJsonLd(ALL_STORES); enhanceStoreIndex();`）を削除したので、同じ場所を触る枝とは両方の変更を取って合流する。
8. **重さの上限を下げる。** `data/page_weight_policy.json` の `top` を 1,500,000 から 800,000 バイトにし、実測（620,619）を記録した。全店の索引が戻れない位置にする。
9. **0021 との関係。** 「正確な数を出す場所」だったトップの見出しの数（全店舗一覧の N 店）はなくなる。エリアごとの軒数とハブの掲載軒数は残る。トップの文章の数は「約5,000」のまま。
10. **計測への影響。** 削除した JS に GA4 のイベント送信（`trackEvent`・`gtag`・`nbReserveExit`）は無く、イベント名とパラメータは変えていない（実ブラウザで前後の送信を比べて同じ）。ただし、旧索引のエリアを開いて出ていたカード（`buildCardHtml(s, 'index')` 経由の `modal_open` と、`cta_click` の `location=card`・`card_media`）は出なくなる。どれだけ減るかの数字は無い。
11. **検査。** `tests/top_light_index.test.js`（19 件。ハブの選び方・区画の生成・ItemList の作り方と現データでの実在・カードのリンクが「現役の店舗ページがある全店に付く」こと・索引が戻れない位置・`LOCAL_STORES` の形と先頭 50 件・CSS のトークン）、`tests/audit_store_reachability.test.js`（6 件。偽のツリーで深さ・誘導ページの除外・孤児・トップの差し替え）、`tests/index_card_compact.test.js` と `tests/selection_wording_sources.test.js` を更新。意図的に壊した 50 通りのすべてでテストが落ちることを確かめた。実ブラウザ（390px・1280px）で、検索・モーダル・♡・並べ替え・ジャンルの絞り込み・索引の開閉・コンソールのエラー 0 を確かめ、計測イベント名が前後で同じことも確かめた。

## 選ばなかった案と理由
- **全店の索引を残して、重さを許す**: オーナーの決定（#7）で外した。トップの 54% を占め、最初の描画の前に全部読み込まれる。
- **条件のハブを含む 694 本を全部リンクする**: 実験で深さの分布が同じ。リンクが長くなるだけ。
- **入口の無い店を、安全網としてトップに足す（約 80 リンク）**: 見送り。上の 3 の理由。影響が数字で出たら足す。
- **同じ PR で、エリアの一覧ページを直す（217 店ぶん）**: 一覧の生成器の変更で、この PR の範囲の外。置き換えの影響を測ったうえで、必要なら別の PR にする。
- **`LOCAL_STORES` の各行に店舗ページの href を持たせる**: 約 5,000 行に 1 項目ずつで、約 180KB 戻る（ID から決まる値を重ねて持つことになる）。
- **`data/stores.json` に href のフィールドを足す**: ID から決まる値を別に持つと、ID が変わったときに食い違う。二重管理になる。
- **STORE-INDEX の「店名（エリア・ジャンル）→ href」の表を別に埋め込み続ける**: 重さが戻るうえ、同名の 2 件が曖昧なまま残る。
- **ItemList を動的生成のまま、または `about` の 3 件のまま残す**: URL が外部の予約サイトや絞り込みで、画面の一覧・店舗ページと対応しない。0029 に沿わない。
- **ItemList に全店を載せる**: 約 5,000 件で重さが戻る。先頭 50 件は、画面の最初の描画と対応する。

## 見直す条件
- **置き換えの影響（検索の数字）**: 置き換え日を境に、+7 日・+14 日・+28 日で見る。基線は PR に表で残した（Search Console の画面の数字は、オーナーがマージ前に取る）。判定の決まりは次のとおり。
  - 置き換え日の前 14 日の幅の内側は「差なし」にする（少しの差は結論にしない）。
  - Search Console の店舗ページの「表示のあったページ数」が、基線（約 3,100・直近 14 日の幅は 2,956〜3,167）から約 10%（約 2,800 以下）下がった状態が、+14 日と +28 日で 2 回続いたときだけ「影響あり」にする。「ページのインデックス登録」の登録済みは、着けなくなった 245 店ぶん（約 5%）を超えて減ったら、別の原因も疑う。
  - 特集・ジャーナルの動きを対照にする（同じ向きならサイト全体の変動）。GSC は 28 日の移動窓なので、+7 日は向きだけ・+28 日で全部が「後」になる。リポジトリには上位 500 ページしか無く、245 店の個別の基線は取れない。
- 「影響あり」のときは、エリアの一覧ページを直す案（217 店ぶん・一覧の生成器の変更）か、トップに約 80 リンク（約 8KB）を足す案を選ぶ。
- 着けなくなった 245 店: エリアの一覧ページに「ジャンル別の一覧ページが無い店」を載せる変更（計画の I-28 と同じ場所）や、「似た店」のつながりの見直しで減るか。そのつど `node scripts/audit_store_reachability.js` で数え直す。夜間の検査に載せるかは、数え直しで増減が続くか次第（今は `--check` を持たない）。
- 手動店 157 のカードのリンク: ページのスラグの解決を別の課題にする。
- `buildCardHtml(r, 'index')`・`nbCardSizes('index')` の枝: 次のカードの整理で外す。
