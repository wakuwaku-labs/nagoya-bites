# 0035 トップの「今日の話題店」と「よく見られている店」を、生成時に本物のリンクとして書く（最初の画面に写真で選べる行を置く）

- 日付: 2026-10-14
- 状態: 採用
- 関連: Linear P-399（親 P-235・UI・UX全面改修・計画の I-24）/ 判断の記録 0026（端末の書体）・0029（トップの構造化データは画面に見える事実だけ）・0031・0032（トップの言い方）・0034 / `scripts/lib/top_picks.js` / `scripts/build_top_picks.js` / `scripts/build_journal_index.js` / `data/ranking_display_policy.json` / `tests/top_picks.test.js` / `tests/build_journal_index_photo.test.js` / `tests/index_top_structure.test.js`

## 背景
- オーナーの指示（2026-10-11）:「クリック数や滞在時間を増やすために、不要な操作を増やすことは避けます。」「回遊を増やすためだけの無関係な推薦は避けてください。」「画面遷移を減らすことだけを目的にせず、ユーザーが迷わず目的を達成できる設計にしてください。」
- トップの最初の画面（スマホ）は、見出し・検索欄・場面とエリアの入口のあと、「今月の特集」の横スクロール（写真 8 枚）が占めていた。探す入口と、写真で選べる店が、最初の画面に並んでいなかった。
- 「今日の話題店」の行は、ページを開いたあとに JS が全店のデータから描いていた。実測で次の不具合があった。
  - インラインの TOP50 には 5 件のうち 2 件しか入っておらず、最初は 2 枚で、全店の読み込み後に 5 枚へ増える（レイアウトがずれ、写真が遅れて出る。検索エンジンにも見えない）。
  - 2026-10-13、選定の 1 位「小菜一碟」が本番の行に出ていなかった。`build.js` の焼き込みは「店名＋エリアの完全一致」で、選定側のエリア（名古屋市東区相生町）と `data/stores.json` のエリア（東区・相生町）が違うため一致せず、CI のログに「マッチ失敗」と出るだけで 4 枚になっていた。
  - 客が投稿した写真（`写真出所=places-user`）の撮影者が行に出ていなかった（今日の 5 件のうち 3 件）。
- 「よく見られている店」（TOP10）は、閲覧数の下限が無く、2026-10-13 の実測は 30 日で 64 件・閲覧のあった店 37 店・うち 10 回以上は 1 店だけだった。「1回閲覧」の店が並んでいた。
- 「この条件で通知」のボタンは、押すと「準備中です — SNSをフォローして最新情報をチェック！」と出るだけで、通知の仕組みは無かった（計測も無い）。
- 最新ジャーナルのカードは文字だけで、記事の顔の写真は載っていなかった。

## 決めたこと
1. **行は生成時に静的な HTML として書く。** `scripts/build_top_picks.js` が `data/daily_trending5.json` などから、`index.html` の目印の間（`TREND_PICKS` / `VIEW_RANKING`）を作り直す。`build.js` の末尾から呼ぶので、`build.yml` と `daily-trending5.yml`（5:30 JST の選定のあとに `node build.js` を回す）のどちらでも効く。何度回しても同じ（冪等）で、目印が無ければ作り直さず警告に出す。
   - 最初の画面には、探す入口（検索・場面・エリア）の下に「今日の話題店」（写真つきの行）を置く。1024px 以上は右の列に縦の一覧、スマホは横に並べ 3 枚目がのぞく。今月の特集は最初の画面の外（hero の直後）へ移す。
   - 「この条件で通知」は外す。仕組みが無い機能を約束するボタンは信頼を損なう。
2. **行は本物のリンク（`a`）にする。** ふつうのクリックは、これまでどおり店の詳細（クイックビュー）を開く（`modal_open` の `source` は行の `data-source`＝`trend_today` / `ranking`）。新しいタブで開く・修飾キー付き・中クリック・全店の読み込み前・同名の店をエリアでも決められないときは、リンク本来の動き（店舗ページへの移動）に任せる。JS が動かなくても、検索エンジンにも、店舗ページへのリンクとして見える。
3. **リンク先は確かめてから書く。** `gen-store-pages.js` の `toSlug` で候補を作り、そのページの `<h1>` が本人の店名か確かめる（スラグが重なった `-2` 以降も探す）。誘導ページ（古い ID）なら誘導先を辿る。確かめられなければ検索のディープリンク（`index.html#q=店名`）に落とす。
4. **選定の 1 件を店舗データに結ぶのは「店名が 1 件ならそれ、複数ならエリアが合う 1 件、決められなければ出さずに警告に理由を書く」。** 黙って落とさない。これで「小菜一碟」が行に戻る。選び方（`scripts/pick_daily_trending5.js`）には触れない。
5. **注目の理由の行は、後から第三者が確かめられる事実だけ（制約 10）。**
   - 「{N}サイトで紹介」＝ `trending_stores.json` / `manual_stores.json` の `出典URL` の別サイトの数（登録ドメインに丸める。`ssl.tabelog.com` と `tabelog.com` は同じ）。
   - 「{M/D}に確認」＝ 選定の日 − `鮮度日数`（選定器と同じ計算）。
   - 作れない部分は出さず、両方作れなければ行ごと出さない。順位の数字・「人気」「話題沸騰」・選定器が数える「媒体数」（トレンド情報源のラベルと出典の別ホストを足した値で、検算できない）は使わない。
6. **「よく見られている店」は、下限にそろう日だけ出す。** `data/ranking_display_policy.json`: 直近 30 日に 10 回以上見られた店が 5 店以上そろったときだけ、多い順に最大 10 店（同数は店名順）。そろわない日は区画ごと出さない（件数が少ない日に数字を盛らない・品質ゲート原則 3）。閲覧数の出どころは GA4 の `modal_open`（`data/view_counts.json`）。閾値の変更はこの JSON で行う。2026-10-13 は下限に届かないので、当面は出ない。
7. **写真。**
   - 客が投稿した写真（`places-user`）には撮影者を出す（`data/photo_policy.json` の `userPhotoRequiresCredit`）。`写真クレジット` の `&amp;` は戻してから 1 回だけ逃がす。写真が無い店は「写真準備中」。
   - Google マップの写真（`lh3.googleusercontent.com`）は、保存してある `=s1600-w1200`（実測 1 枚 100〜560KB）のままだと最初の画面の 5 枚で 1.58MB になる。カード用には、同じ CDN・同じ写真の大きさの指定だけを `=w480`（`srcset` は `w320`・`w480`）に替える。保存・加工・プロキシ・再配信はしない（既存の直接配信と同じ扱い）。ほかの写真（ホットペッパー等）は `index.html` の `nbImage` / `nbSrcset` と同じ URL にする（テストが実データの全 URL で突き合わせる）。
   - 最初の画面の画像の転送量（DPR 3・キャッシュなし）: 1.17MB（今月の特集の 8 枚）→ 0.32MB（話題店の 5 枚）。
8. **最新ジャーナルのカードに、記事の顔の写真と出所を添える。** 写真は記事自身（`journal/<slug>.html`）の `figure.art-hero-img`（`data-hero-source` が places / press / hotpepper で `data-hero-store` と出所のキャプションがそろうもの）から読む。ここで新しく選ばない（写真の帰属の判定は `scripts/lib/hero_photo_gate.js` が生成時に済ませている）。出所のクレジットは記事と同じ文で、リンクは `https` のものだけ（プレスリリース写真は発行企業名とリリースへのリンクが条件）。読めない記事・形が違う記事は文字だけのカードに戻し、例外は出さない（日次ジャーナルの処理を止めない）。カードは `article` にして、リンクはタイトルだけに張り、カード全体を覆う（出所のリンクと入れ子にしない）。
9. **検査。** `tests/top_picks.test.js`（35 件）・`tests/build_journal_index_photo.test.js`（13 件）・`tests/index_top_structure.test.js`（13 件）。意図的に壊した 61 通りのすべてで落ちることを確かめた。**区画の中身がいまのデータと同じかどうかは検査しない**（routine の PR は `data/` だけを変えて `index.html` を作り直さないため、検査すると自動マージが止まる。作り直しは `build.js` が毎日行う）。

## 選ばなかった案と理由
- **行を今までどおり JS で描き、TOP50 に 5 件を足す**: 最初の画面の写真が遅れて出る・検索エンジンに見えない問題が残る。インラインのデータを増やすと、トップの重さ（I-25 で減らす対象）も増える。
- **`build.js` の焼き込み（`今日の話題` のフラグ）のエリアの一致をゆるめる**: この行はもうそのフラグを読まない（読み手は消した古い描き方だけ）。フラグは `store_dedup.js` が編集項目として扱っているので、外すのは `LOCAL_STORES` を軽くする I-25 で、データの形ごと扱う。それまで焼き込みは変えない（行には影響しない）。
- **理由の行に選定器の「媒体数」を使う**: 検算できない（制約 10）。
- **「よく見られている店」を下限なしで出す**: 「1回閲覧」の店が並ぶ。件数が少ない日に数字を盛ることになる。
- **「よく見られている店」を消す**: 閲覧数が増えれば、事実にもとづく見つけ方として役に立つ。下限で守れる。
- **Google マップの写真を `wsrv.nl` などの変換サービス経由にする**: プロキシできない既存の取り決め（`nbImage`）に反する。大きさの指定だけを替えれば足りる。
- **ジャーナルのカードの写真を、カード用に新しく選ぶ・生成する**: 記事の顔は生成時の判定を通したものだけ。別の写真を選ぶと、その記事の店でない写真を使う危険がある（ISSUE-090）。
- **カード全体を 1 つの `a` にする**: 出所のリンク（Google マップ・プレスリリース）が入れ子になり、HTML として不正になる。

## 見直す条件
- 閲覧数の下限（10 回・5 店）: `modal_open` の件数が増えたとき、または下限に届かない状態が続くとき。GA4 の内部トラフィック除外（2026-10-12 から有効）の前の数には、運営側の閲覧が混ざっている。
- I-25（トップを軽くする）: `LOCAL_STORES` の `今日の話題*` の焼き込みを外す。
- 新しい言い方（「今日の話題店」「{N}サイトで紹介」「{M/D}に確認」「よく見られている店」「直近N日」「{N}日で{n}回閲覧」「写真準備中」）は、オーナーの確認待ちの言い方の一覧に入れる。
- Google マップの写真の大きさの指定（`=w480`）: 写真の配信元の仕様が変わったとき、または画質に問題が出たとき。
