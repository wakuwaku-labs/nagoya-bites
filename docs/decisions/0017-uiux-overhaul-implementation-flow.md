# 0017 UI・UX全面改修は、改善案ごとの PR で段階の順に進め、main へはレビューとオーナーの承認の後に入れる

- 日付: 2026-10-11
- 状態: 採用
- 関連: Linear P-235（親）・P-237（オーナーの決定）・P-239（I-08）/ backlog DSN-013 / `docs/uiux-overhaul-plan-2026-10.md`（4.4 節 #1・第9章）/ PR #470（I-01）・#471（I-08）

## 背景

- 設計書を作った時点では、オーナーは「この段階では既存コードを変更しないでください。実装は承認後に開始します」と指示していた。設計書の 4.4 節 #1 が「計画全体の承認」（推す案は段階0 → 1 → 2）の問いだった。
- オーナーは設計（再設計を含む）の報告を受けた後、「進めて」とだけ返した（2026-10-11）。
- 4.4 節の #2〜#11（文案・Web フォント・外部の画像変換サービス・店舗の索引・404・FAQPage・`journal-today.md`・CLAUDE.md の競争優位の書き方など）は、この返事では決まっていない。

## 決めたこと

1. 「進めて」を、4.4 節 #1 への回答（計画全体の承認。段階0 → 1 → 2 の順に着手）として扱う。
2. #2〜#11 は未決のままにする。これに関わる改善案は、実装と PR までは進めてよいが、**main へはオーナーが決めた後**にする。
3. 実装は**改善案ごとに別のプルリクエスト**にし、1つずつ出す。効果と副作用を見てから次へ進む（設計書 9.1 節）。
   - 作業は origin/main から切った別ブランチと別の worktree で行う。設計のブランチ（wakuwaku-labs/mooneye）には設計書と HANDOFF だけを置き、実装を混ぜない。
   - 各プルリクエストに Linear の課題（P-235 の子）を作り、確かめたことと残りをコメントに残す。
4. main への合流は、Codex のレビューの後。4.4 節で「要」とした改善案は、さらにオーナーの承認の後。Claude は自分では main に入れず、デプロイもしない。
5. 計測を変える改善案は、マージ後に `data/measurement_changes.json` へ日付つきで書く（比較に段差が出るため）。台帳は commit や PR で確かめられる変更だけを書く決まりなので、マージした日と PR 番号が決まってから別のコミットで出す。
6. GA4 の画面など、オーナー本人の操作が要るものは、Linear に `担当:オーナー作業` で分けて起票する（P-240）。

## 選ばなかった案と理由

- 「進めて」を全項目（#1〜#11）の承認とみなし、文案や外部サービスの利用まで進める案: オーナーの返事は一言で、#2〜#11 の中身（特に人が選んだと読める表現や外部サービスの利用）は指示と衝突しうる。取り消せない外向きの変更を、確かめずに入れない。
- 段階0をまとめて1つのプルリクエストにする案: 1つが不具合を出したとき、原因の切り分けと取り消しが難しい。I-01 は main のテストの失敗を直すもので、I-08 の計測とは性質が違う。
- 設計のブランチにそのまま実装を積む案: 設計書の合流と実装の合流が結びつき、片方だけを止められなくなる。

## 見直す条件

- オーナーが #2〜#11 を決めたとき（決まった項目から、main への合流の条件を外す）。
- オーナーが進め方（1つずつ・レビューの後）を変えたとき。
- Codex のレビューが受けられない状態が続くとき（レビューの代わりを決めるのはオーナー）。
