## 0. 骨子（ここだけ読めば全体が分かる）

### 0-1. 何を作るのか（3行）

1. **記事の中身を「判断材料」の形にそろえる。** 確認できたこと・編集部の分析・分からないこと・来店前に確かめたいこと・向く人／向かない人を、出所と確認日つきで出す。
2. **書いた内容を、書き手と別の仕組みが出典と照らして確かめてから公開する。** 確かめられない文は「未確認」に落とすか、その日は出さない。
3. **いま読者を誤解させうる表示を先に直す。** 裏づけの無い「掲載歴」、番号つきの星の順位、言い過ぎの言い切りなど。

## 1. 設計（依頼の 4-1〜4-7）

### 1-1. 独自の編集基準（4-1）

**考え方**: 専門知識を「それらしい文体」ではなく、「何を確かめるか」と「事実をどう読み替えるか」の規則にする。規則は1つのデータ（`data/editorial_standard.json`・新設）に置き、書き手の指示・検査・記事の部品が同じものを読む。今の `agents/editor.md` は推薦理由と来店の導線が中心で、注意点・確認日・事実と推測の区別の指示が無い（`evidence/audit-G-decisions.md` 0-1 の9）。

**(a) 何を確かめれば失敗が減るか — 「来店前に確かめたいこと」定型7項目**

| 項目 | 確かめる先（優先順） | 読者向けの書き方の例 |
|---|---|---|
| お通し・席料 | 店の公式 → ホットペッパーの料金備考 | 「お通し代 300円（ホットペッパー掲載・11月16日確認）」 |
| サービス料・深夜料金 | 同上 | 「記載が見つからなかった（公式・ホットペッパーを11月16日に確認）」 |
| 席の時間制 | コースのページ・公式 | 「飲み放題は120分、注文は30分前まで＝実際に頼めるのは90分」 |
| コース必須・最少人数 | コースのページ | 「個室は4名から・コース注文が条件」 |
| 予約・キャンセル | 予約ページ | 「前日以降のキャンセルは料金の50%」 |
| 支払い方法 | 公式・掲載情報 | 「現金のみ」 |
| 喫煙 | 掲載情報 | 「全席喫煙可」（向かない人の材料になる） |

**(b) 事実の読み替えの規則（専門知識の入れ場所）**

- 例: 「コース4,000円・税込・お通し別300円」→「1人あたりの支払いの目安は4,300円（計算式を出す）」。
- 例: 「カウンター8席のみ・予約不可」→「入れる時刻は確かめられない。開店時刻に合わせるのが確実」。
- 例: 「★4.9・12件」→「件数が少なく、評価は振れやすい」。
- 規則は「元になる事実 → 読者向けの言い換え → 根拠（計算式か一般則）」の3点で持つ。**元になる事実が台帳（1-2）に無い言い換えは書けない**ようにする。これで「専門家らしいが根拠の無い文」が機械的に止まる。
- 今の店紹介に多い経営側の言い回し（「需要を独占供給」「差別化必須」など。特集56本・店舗ページ1,337本）は、読者の判断に使えないので規則に入れない。

**(c) 情報源の優先順**

1. 店の公式の発表（公式サイト・公式 SNS・プレスリリース）
2. 予約・掲載サイトに店が出している情報（ホットペッパー）
3. 地図の事業者情報（Google に店が入れた情報・営業状態）
4. 第三者の報道
5. 口コミ・個人の SNS 投稿 … **事実の根拠にしない。** 本文も転載しない（Google の口コミは規約で保存不可。`evidence/audit-F-data.md` 問い3）。

**(d) 情報源が食い違うとき**: ①日付の新しい方 → ②同じ頃なら店の発表 → ③解けなければ両方を日付つきで並べ「予約のときに店へ確かめてください」→ ④店の実在・住所・開店日・閉店の食い違いだけは公開を保留して人へ（1-4）。

**(e) 口コミの偏りへの対処**: 評価は「数字・件数・時点」の3点セットでしか書かない。30件未満は「件数が少ない」と添える。開店から90日以内は「開店直後」と添える。「驚異的」「異例」などの形容で結ばない。口コミ特典の案内を店が公表していれば事実として書く。

**(f) 注意点の書き方**: 店を評する形容ではなく「条件 → 誰に合わないか」で書く（例: 「全席喫煙可。煙が苦手な人には向かない」）。出所の無い注意点は書かない。

**(g) 未確認の表示**: 定型7項目のうち確かめられなかったものは、必ず「確認できなかったこと」に項目名・確認先・確認日を書く。空欄にしない。

**(h) 記事の種類ごとの必須情報**

| 種類 | 今の資産 | 必須にするもの |
|---|---|---|
| 話題のお店紹介 | 日次ジャーナルの「今日の1軒」など（193本中94本） | 状態の帯（確認日・未訪問・開店前か）／確認できたこと／来店前に確かめたいこと／向く人・向かない人／出典と確認日 |
| 店選びガイド | ジャーナルの解説の回（32本）、特集の「選び方」の節 | 一般則とその根拠／読者が自分で確かめる手順／掲載データの集計を使うなら対象件数と取得日 |
| 比較・特集記事 | 特集73本 | 比べる物差しの明示／店ごとの確認メモ（同じ項目を同じ順で）／選んだ条件の開示／番号で順位を付けない（→決定1） |

**(i) 利用目的に合わせた比較**: 目的（一人・デート・接待・宴会・家族）ごとに比べる項目を決めておく。手本は既にある（`features/nagoya-solo-dining.html:265-272` の見分け方の表、`features/date.html:198-203` の「予約前に確かめる4つ」）。

### 1-2. 情報の信頼性管理（4-2）

**記事ごとの「事実台帳」**（新設。`data/journal_claims/<日付>.json`）。本文の事実の文1つにつき1行。

| 項目 | 中身 | 依頼の項目との対応 |
|---|---|---|
| text | 本文の該当の文 | — |
| kind | 確認済みの事実／口コミの数字／編集部の分析／未確認 | 情報の種類 |
| source | URL・発行元・種類（公式／掲載サイト／地図／報道）・掲載日 | 情報源 |
| evidence_quote | 出典からの短い引用（最大120字） | 根拠となる記述 |
| fetched_at | 機械が出典を取得した日時 | 取得日時 |
| confirmed_at | 記事に出す確認日 | 確認日時 |
| status | 照合できた／取得できず照合不能／食い違い／古い | 確認状況 |
| recheck_after | 見直す日（開店前の記事は開店日+7日、価格は90日、期間限定は終了日） | 更新の必要性 |
| rights | 引用／リンクのみ／報道用の許諾／API の規約 | 利用権限 |

- 既にある型を広げる。`data/editor_picks.json` の `sources[]`（URL・抜粋・何を支えるか・取得日。275件）と、X の文面の「数字が記事の引用にあるか」の検査（`scripts/lib/x_post.js:235-239`・決定記録 0047）が同じ考え方。
- **公開リポジトリに第三者のページ全文を置かない。** 残すのは URL・取得日・短い引用・全文のハッシュ（中身が変わったかを後で確かめる用）だけ。全文は Mac の中（`.local-logs/`）に置く。
- 店舗データ: ホットペッパー由来の項目には店ごとの取得日が無いが、毎回のビルドで全件取り直している（`data/hotpepper_fetch_log.json`）。店舗ページには「ホットペッパー掲載情報（◯月◯日取得）」をビルド日で出せる。Google の評価は店ごとの算出日（`reviewTrust.d`）がある。
- 口コミ・SNS の扱い（今の決まりを維持）: Google の口コミ本文は保存しない。Instagram は公式の埋め込みだけ。食べログはリンクだけ。**Instagram の説明文7,939件を公開リポジトリに保存している点は規約上の決めが無い**ので、④の「後で要る判断」に載せた。
- 自動で取れないもの（提供スピード・接客・清潔感・写真と実物の差）は台帳の項目に入れない。取れる前提の設計をしない。

### 1-3. AI 品質審査（4-3）

**総合点で合否を決めない。** 今の採点（100点以上で合格・85点以上で注記つき合格）は「題材選び」の段として残し、公開の可否は次の**独立した停止条件**で決める。1つでも当たれば自動公開しない。

| 停止条件 | 判定の方法（誰が見ても同じ結果になるもの） |
|---|---|
| 事実の誤り | 本文の数字・日付・価格・営業情報が、台帳の引用の中に無い |
| 根拠不足 | 「確認済みの事実」と書いた文に出典が無い。または出典を取得したのに引用が見つからない |
| 権利の問題 | 写真の帰属（今の検査 15〜15d）。引用の長さの上限超え。口コミ本文の転載 |
| 重大な誤認 | 行っていない店を行ったように書く（11-16 に検査済み・決定記録 0068）／人が選んだと読める言い方／編集部独自の順位・点数／サクラ・品質の断定／Google が閉業・休業と返した店を営業中として紹介 |
| 核心の食い違い | 店の実在・住所・開店日が情報源どうしで合わない |
| 型の欠落 | 状態の帯・確認日・「確認できなかったこと」・注意点のどれかが無い |

**3つを組み合わせる**（依頼の「自己評価だけに依存しない」）:

1. **出典との照合（機械）**: ラッパー（毎朝の実行の外側の台本）が出典 URL を**自分で取り直し**、台帳の引用がそのページに在るかを確かめる。書き手の「取得しました」という申告は使わない。
2. **決まりの検査（機械）**: 上の表。今の検査（`scripts/validate_journal_draft.js` の22項目）に足す。
3. **独立した読み手（別の AI の呼び出し）**: 書き手の文脈を持たない別プロセスに、記事と「機械が取り直した出典の抜粋」だけを渡す。道具は持たせない（出典ページに仕込まれた指示に従う危険を避ける）。出力は点数ではなく「本文のこの文は、出典のこの記述と合わない」という所見の列。**所見は機械で再確認できたものだけ停止条件に使い**、再確認できないものは記録に留める（品質ゲートの決まり＝自己申告値を合否に使わない、を守る）。

出典を取得できないサイトはある（食べログは9月20日からリンクの照合が止まっており、取得を拒否されている疑いがある。原因は未確認）。その場合は「照合不能」と記録し、その文は「未確認」に落とす（1-4 の自動修正）。**取得の成功率は試運転で最初に測る**（今は未測定。取れる前提にしない）。

### 1-4. 自動公開（4-4）

| 道 | 条件 | 動き |
|---|---|---|
| 自動公開 | 停止条件0件 | 今と同じ流れで公開。台帳と検査の記録を残す |
| 自動修正・再検査 | 照合不能の文、型の欠落、言い換えで直る表現 | 該当の文を「未確認」に書き直すか削る → 全部の検査をやり直す。**最大2回**。それでも駄目なら、採点済みの次の候補の題材で1回だけ書き直す |
| 公開保留・人の判断 | 核心の食い違い／権利の不明／2回直しても消えない誤り／記事の柱になる事実が照合不能 | その日は出さない。Ondine に本人宛ての課題を自動で作る（何が・なぜ・選択肢）。X と note も出ない（公開の台帳に載らないので、今の仕組みのまま自然に止まる） |

- **公開停止（取り下げ）**: 新しい道具 `scripts/journal_withdraw.js`。記事を「取り下げました（日付・理由）」の短いページに差し替えて検索に出さない設定にし、一覧・配信・関連リンクから外し、台帳に取り下げと記録し、X の投稿を消し（既存の `x-delete.yml`。11-13 に2回失敗しているので先に直す）、検索エンジンへ通知する。今は手作業の git だけ（`evidence/audit-C-pipeline.md` 1-10）。
- **訂正**: 台帳に訂正の記録（いつ・何を・なぜ）を持ち、記事の末尾に「訂正の履歴」を出す。黙って書き換えない。
- **ロールバック**: 新しい検査の段は設定1か所（`data/journal_gate_policy.json` に足す `claims_gate: off / shadow / enforce`）で切り替える。問題が出たら `shadow` に戻すだけで、今の公開条件に戻る。
- **重複公開の防止**: 今の仕組みで足りる（当日分が公開済みなら終了、同じ店は30日・候補段階で90日、題と冒頭の類似）。**変更不要。**
- **監査の履歴**: `data/journal_audit/<日付>.json` に、使ったモデル・指示文の版・採点・各検査の結果・所見・出典の取得結果・どの道を通ったか、を残す。今は調査のメモが一時フォルダにあり翌日には消える。
- **本番の条件を変える手順**: 最初は `shadow`（記録だけ。公開には影響しない）。4章の S4-5 の検証に通り、本人が承認して初めて `enforce` にする（→決定6）。

### 1-5. 既存記事の改善（4-5）

- **選び方**: 検索での表示・クリック（直近28日）× 問題の重さ。台帳 `data/article_review_ledger.json` を機械で作る。
- **重さの順**: ①事実と違う・裏づけが無い（掲載歴・訪問済・休業中の店）→ ②誤解を招く（星の出所の取り違え・順位）→ ③判断材料が足りない（注意点・確認日）→ ④古い（季節切れ）。
- **流入のある記事は足すだけ**: 題・URL・大見出し・冒頭の文・章の並びは変えない。店ごとの確認メモ、星の書き方、向かない人の1行、出所と確認日の枠を足す。変えてはいけない部分は機械で固定する（題・大見出し・冒頭150字の控えを取り、差が出たら止める）。
- **重複の統合**: 掲載店の8割が同じ焼き鳥の2本など（→決定7）。GitHub Pages は転送の設定が出来ないので、正規の URL の指定＋転送用のページで寄せる。
- **品質不足の記事**: 検索にほぼ出ない特集52本は個別に書き直さない。機械で入る部品（星の書き方・番号の扱い・出所の枠）だけ当て、季節が終わった5本は「いつの内容か」を冒頭に書いて検索に出さない設定にする。

## 3. 段階のつながり

```
段階0（方針の正本化）─┬─ 段階1（誤解を招く表示）──────────────┐
                      ├─ 段階2（出所と確認日）─┬─ 段階3（記事の型）─┬─ 段階5（既存記事）

                                         本人の承認（決定6）→ 本番の条件    段階6（トップ）→ 段階7（測定）
```

- 同時に進められる: 段階1・段階2・削減。段階3と段階4の前半。
- 本人の決定を待つ施策は印を付けた。**決定が出ていなくても進められる施策が先に来る**ように並べてある（決定待ちで全体が止まらない）。

## 6. 組織（増やさない）

- 新しい役割・新しいエージェントは作らない。
- 記事の流れは「書き手（今の Editor の指示）→ 機械の検査 → 独立した読み手（今の検証役の文書に節を足す）→ 3つの道 → 保留は Ondine の本人宛て課題」。全部、今ある仕組みの型の使い回し。

- 人に来る確認は3種類だけになる: ①記事の保留（核心の食い違い・権利の不明）②取り下げの判断 ③方針の変更。今ある「選定理由の承認」「閉業の確定」などのうち、前者は無くす提案（決定8）、後者は残す（店を誤って消さないため）。
