# /seo-triage-weekly — 週次レポートのAI分析をブランドフィルターに通して課題化する

毎週 LINE に届く週次レポートの「🤖 AI週次分析（前週比）」と「💡 今週のアドバイス」を、
**鵜呑みにせず** NAGOYA BITES のブランド・方向性という総合フィルターに通し、
適合分だけを Notion 課題トラッカーに `ready` で出す。却下は理由とともにログへ残す。

日次の `/seo-triage` と**完全に同じ仕組み・同じスクリプト・同じ Notion 同期**を使う。
違いは入力が「週次レポート（前週比トレンド付き）」であり、`source` を `line-weekly` で記録する点だけ。

**使い方**: LINE の週次レポート本文をこのコマンドに続けて貼り付ける。
（引数が空なら「週次レポート本文を貼ってください」と尋ねる。）

---

## 前提（このループの記憶 — 日次と共有）

- 採用課題マスター: `agent-backlog.md`（ID 接頭辞 `SEO-` / owner=Marketer / category=SEO）
- ループの記憶（採用・却下・重複の全履歴）: `data/seo_advice_log.json`（append-only・`source` で日次/週次を区別）
- 決定的ヘルパー: `node scripts/seo_triage.js`（ID採番 / 重複検知 / ログ追記 / 健診レポート）
- Notion 同期: 既存の `/sync-backlog`（スキーマ変更不要・そのまま流用）

---

## 実行フロー（必ずこの順番）

### Step 1: ブランドフィルターの根拠をロード

`CLAUDE.md` の以下2ブロックを**毎回読む**（規約が更新されたら判定も自動追従する）:
- 「**我々の Moat**」「**我々が勝つ領域**」 → 採用の方向
- 「**戦わない領域 — Strategic Skip**」＋「絶対に守る制約」7・8（信頼毀損禁止 / マネタイズは承認制） → 却下の方向

ハードコードした禁止ワードで機械判定しない。**総合的な編集判断**を行うのがこのコマンドの役目。

### Step 2: 週次レポートを施策候補に分解

週次レポートは日次と構造が違う。**2種類**の入力源を施策候補にする:

1. **🤖 AI週次分析（前週比）の総括文** — ここが週次の肝。
   - 前週比で大きく動いた指標（例:「検索流入が前週比 -32%」「予約クリックが +50%」）は、
     **単日のブレではなく週トレンド**なので、施策化の優先信号が強い。
   - 「落ちた」トレンド → 原因調査・テコ入れ課題（多くは P1〜P2）
   - 「伸びた」トレンド → 勝ち筋を伸ばす課題（横展開・内部リンク強化など P2）
   - 総括が現状描写だけでアクションに落ちないなら、**自分でアクション仮説を1つ立てて**候補化する
     （週次は「気づき→打ち手」への変換がこのコマンドの価値）。

2. **💡 今週のアドバイス（3件）** — `🔴`/`🟡`/`🟢`/`💡` ＋ `👉` で1施策の区切り。
   - 各 `👉` を1施策候補に割る。AI生成＋ルールベース保険が混在することがあるので主旨が重複するものは1つに。

「📈 成長ステータス」「人気ページ TOP5」などの**数値・ランキング表示のみ**はアクションが無ければ起票しない。

### Step 3: 重複チェック（二重起票防止・日次ログとも横断）

各候補について:
```bash
node scripts/seo_triage.js --check-dup "<その施策のテキスト>"
```
- `duplicate: true` → 過去に判定済み（**日次で採用済みの同種施策とも衝突する**＝重複は良いこと。二重実装を防ぐ）。
  **起票しない**。ログには `verdict: "duplicate"` で軽量追記のみ。
- `duplicate: false` → Step 4 へ
- 数値違いは正規化で同種扱い（「流入-32%」「流入-28%」は同じ施策とみなす）。

### Step 4: ブランド判定（採用 / 却下）

各候補を1件ずつ、Step 1 の根拠に照らして判定する。判定基準は日次 `/seo-triage` と同一。

**却下（rejected）にする** — backlog には出さず、ログのみに理由付きで残す:
- Strategic Skip 抵触: 匿名口コミの大量集積（食べログ型）/ クーポン・予約特典経済（ホットペッパー型）/
  高級セグメント特化（一休型）/ 女性向け装飾演出（OZmall型）/ 雑誌・印刷連動 / 月刊スピード追従
- 順位操作・自作自演・サクラ・実在しない店の掲載を促すもの（信頼担保に反する）
- 広告主依存・PR記事・送客手数料に誘導するもの（編集独立性に反する。制約7・8）
- 汎用ストック写真の使用を促すもの（写真ソース優先順に反する）
- 効果が薄い・汎用論・精神論で具体性が無いもの

**採用（adopted）にする** — `agent-backlog.md` に `ready` で起票:
- Moat を伸ばす方向: シーン別専門性（宴会・接待・デート等）/ 業界人の目利き / 編集独立 /
  構造化DB（4,500店超）の活用 / 自社特集・日次ジャーナルの自然強化
- 前週比で落ちた指標の原因調査・テコ入れ（順位を歪めない範囲で）
- 順位を歪めず、既存の実在データ・実写・特集を強化する施策
- 独自KW（「業界人 推薦」「予約困難 理由」等）で検索面を広げる施策

**判断に迷うグレーは「採用（要検討メモ付き）」**にしてユーザーの目に触れさせる。
ユーザーが「全部間に受けない」と明言しているので、**疑わしきは却下に寄せつつ、却下理由は必ず明記**する。

### Step 5: 採用分を agent-backlog.md に起票

採用が複数あるなら ID は連番。先頭IDを取得:
```bash
node scripts/seo_triage.js --next-id   # 例: SEO-004。2件目以降は連番で手当て
```

`agent-backlog.md` の「## 進行中・完了タスク」直下に、既存パーサ準拠の形式で追記する
（`**priority** / **status** / **detected** / **category** / **owner**` を必ず含める。これが無いと Notion 同期で欠落する）:

```markdown
### [SEO-004] <施策を一言で・効果が伝わる動詞で>
- **priority**: P2 → **status**: ready
- **detected**: <今日の日付 YYYY-MM-DD>
- **category**: SEO
- **owner**: Marketer
- **source**: 週次レポート(LINE) <週の範囲 例 2026-05-25〜05-31> 原文「<該当の総括 or アドバイスを短く引用>」
- **brand-filter**: ✅ 適合 — <Moat のどこを伸ばすか / なぜ順位操作でないか>
- **trend**: <前週比の根拠。例: 検索流入 前週比 -32%（週トレンド）>
- **acceptance**: <受け入れ条件。例: 対象特集のh1/タイトル/本文冒頭2行にKWを自然挿入・JSON-LD不汚染・効果は翌週の週次レポートで再評価>
```

優先度の目安: 信頼に関わる/前週比で大きく落ちた指標の原因対応=P1 / 集客・SEO強化=P2 / 磨き込み=P3。
週次トレンド由来は、**落ちトレンドは P1〜P2 に寄せる**（週で続く悪化はブレではなく構造問題の可能性）。
owner は実装者で振り分けると `/solve-next` が正しいエージェント仕様を読む（index.html=Builder / journal・features=Editor / 集客企画=Marketer）。

### Step 6: 全項目をログに記録（source は line-weekly）

採用・却下・重複の**全項目**を1回でログ追記（配列で渡せる）。**`source` に必ず `line-weekly` を入れる**:
```bash
node scripts/seo_triage.js --log-append '[
  {"id":"SEO-004","date":"<日付>","source":"line-weekly","advice":"<原文>","verdict":"adopted","brand_reason":"<採用理由>","category":"SEO"},
  {"id":null,"date":"<日付>","source":"line-weekly","advice":"<原文>","verdict":"rejected","brand_reason":"<却下理由 — どの Strategic Skip に抵触したか>","category":null}
]'
```
`fingerprint` は省略可（スクリプトが正規化して自動付与 → 次回の重複検知に効く）。
`source` を省くと既定 `line-daily` になるので**週次では必ず明示**する。

### Step 7: Notion へ同期

採用が1件以上あれば `/sync-backlog` のフローを内部実行する:
```bash
node scripts/sync_backlog_to_notion.js --if-changed
```
`changed: true` なら `/sync-backlog` の手順で MCP 経由 create/update を実施。
採用課題が `ready / 担当部署 / カテゴリ` で Notion 課題トラッカーに出現する。
（採用ゼロ＝backlog 無変更なら同期はスキップしてよい。）

### Step 8: トリアージ表を提示（可視化＋上書き余地）

ユーザーに**採用・却下の両方**を理由付きで見せる。週次は前週比トレンドの根拠も併記する:

```
## 🧭 週次レポート トリアージ（<週の範囲>）

### 📈 今週のトレンド要約（AI週次分析より）
- <総括を1〜2行で。最も動いた指標を数値付きで>

### ✅ 採用 → Notion に ready で起票（N件）
| ID | 施策 | 前週比の根拠 | ブランド適合理由 | 優先度 |
|----|------|--------------|------------------|--------|
| SEO-004 | … | 検索流入 -32% | Moat「シーン別専門性」を強化 | P1 |

### ⛔ 却下 → ログのみ（M件）
| 施策 | 却下理由（抵触した方向性） |
|------|----------------------------|
| クーポンで予約増 | Strategic Skip「クーポン経済」— 広告主依存に陥る |

### 🔁 重複スキップ（K件）
- … （日次/過去週で判定済み。再起票せず）

---
次アクション:
- このまま実装に回すなら `/solve-next`（着手時に YES を確認します）
- 判定を変えたい場合は「SEO-004 は外して」「却下した○○はやっぱり採用」と言ってください → 即修正します
- 週次ループの健診: `node scripts/seo_triage.js --report --days 90 --source line-weekly`
```

**既定は自動**（採用は自動で ready 化）だが、表で全件見せることでユーザーがその場で上書きできる。

## 重要な原則（日次 /seo-triage と共通）

- **鵜呑み禁止**: アドバイス・トレンド要約は必ず Step 1 の根拠を通す。却下には必ず理由を残す。
- **週トレンドは単日より重い**: 前週比で続く悪化/改善は「ブレ」ではない。落ちトレンドは原因調査を優先度高めに。
- **実装は別ゲート**: ここで作るのは `ready` まで。実装着手は `/solve-next` の YES ゲートを通る。
  マネタイズ・信頼に関わる施策は CLAUDE.md 制約7・8により**さらにユーザー承認が必須**。
- **1ファイル制約は不変**: サイト本体は `index.html` 単一ファイル維持。
- **写真は実写優先**: KW施策で画像追加が要るなら写真ソース優先順（公式IG embed → HotPepper → Places → 自作SVG）に従う。

---

## エラー時

- 貼り付けが空 → 「LINEの週次レポート本文を貼ってください」と促して終了
- `--check-dup` / `--log-append` がエラー JSON を返す → ユーザーに内容を見せて中断（ログ不整合を防ぐ）
- Step 7 の Notion 同期失敗 → backlog 起票は完了しているので、その旨を伝え「後で `/sync-backlog` 再実行」を促す
